# SGEG v2 架构设计

> SGEG v2 的目标形态：内核侧收敛为一个**默认关闭、启用即强制**的安全模块，只保留主体标签、客体标签、转移规则、判定四个原语；身份、策略语言、可信启动与审计消费全部退到用户态。新增 syscall 数为 0，既有 `SYS_SGEG_*` 编号整体作废。

## 标注约定

本文所有决策级陈述按来源分三类，行文中逐条标注：

- **［用户裁定］**：用户明确拍板、可直接作为施工前提的结论；
- **［讨论共识］**：讨论中已达成一致并经用户认可，但未以"裁定"形式固定，仍可被新证据推翻；
- **［待定］**：AI 建议、候选方案或尚未闭合的分歧，用户未裁定。全部集中在"开放议题"章，逐条给出待定原因、备选与各自代价。

未标注的内容是**可核查事实**或**基于事实的推导**，不构成决策。本文的周期数与百分比一律是推算量级，不是实测读数。

本文描述的是 SGEG v2 的目标形态；文件名不带版本后缀，版本信息只由正文承载（见 OQ-5）。

事实类引用统一给源码路径与行号；规模数字采用当前代码的可复现实测口径。早前记录中的"约 45 条分发臂、约 96 个类型常量"来自不同统计口径的估算，与当前代码不符，本文不沿用估算值，避免把口径差异写成设计前提。

## 设计动因：一个名字承担了三层职责

### 现状规模与形态

SGEG 当前是一个横跨两个子树的完整子系统：

| 项 | 实测 |
|---|---|
| 代码规模 | `privileged/sgeg` 13 个文件 + `functions/sgeg` 17 个文件（含 `storage/` 2 个），合计 30 个文件、9,302 行 |
| syscall 编号 | 32 个 `SYS_SGEG_*`，占用 400–463 段（[types.rs:627](src/kernel/privileged/syscall/types.rs) 起） |
| 分发臂 | `functions/syscall/dispatch.rs` 33 条（`SYS_SGEG_DISK_INSTALL` 因 cfg 分两条），覆盖 [dispatch.rs:1375-1530](src/kernel/functions/syscall/dispatch.rs) |
| 类型 / 能力常量 | 分散在多处：`privileged/sgeg/capability.rs` 46 个 `pub const`、`privileged/sgeg/types.rs` 30 个、`functions/sgeg/policy.rs` 26 个 |

需要先肯定一点：SGEG 不是完全的空转摆设。seccomp 检查确实位于 syscall 分发硬路径（`privileged/syscall/dispatch.rs` 与 `privileged/proc/seccomp.rs`），文件系统的 `open`、`access`、`mount`、`link` 路径也确实调用能力检查。问题不在"完全没做"，而在"做的位置与承担的职责不匹配"。

### 四个致命缺口

**其一，身份不可持久。** 身份表落盘路径是 `/pwm.db`（[persist.rs:22](src/kernel/functions/sgeg/persist.rs)），`save_database` / `load_database` / `remove_database` 在 [persist.rs:203](src/kernel/functions/sgeg/persist.rs)、[persist.rs:255](src/kernel/functions/sgeg/persist.rs)、[persist.rs:326](src/kernel/functions/sgeg/persist.rs) 定义，随后只被 SGEG 内部的包装层调用（[crypto.rs:304-333](src/kernel/functions/sgeg/crypto.rs)、[identity.rs:114](src/kernel/functions/sgeg/identity.rs)、[identity.rs:480-494](src/kernel/functions/sgeg/identity.rs)），启动编排只调用 `sgeg_init`（[lib.rs:919](src/kernel/lib.rs)），既不加载也不保存。这意味着**创建过的身份在重启后消失**，持久化机制存在但没有接线。

**其二，启动零信任。** `sgeg_init` 用全零公钥初始化（[mod.rs:66-72](src/kernel/privileged/sgeg/mod.rs)），而 `SecureBootSubsystem::init` 只要收到任意公钥就 `enabled.store(true)`（[secure_boot.rs:185-199](src/kernel/privileged/sgeg/secure_boot.rs)）。启动路径没有任何镜像校验，`verify_image`（[secure_boot.rs:228](src/kernel/privileged/sgeg/secure_boot.rs)）只能由 syscall 主动调用。于是 `enabled = true` 的真实含义是"有一个公钥"，不是"启动镜像已验证"。同一份报告也确认：`boot_check_syscall` 只查身份存在性，验签失败不硬阻断（[subsystem-gap-deep-audit.md](docs/report/subsystem-gap-deep-audit.md)）。

**其三，能力检查是库，不是强制点。** 检查散落在 `functions/fs` 的少数入口：`open`、`path`、`mount`、`link` 以及 SGEG 自身接口，例如 [path.rs:91-92](src/kernel/functions/fs/path.rs) 的硬编码 `0x01` 判断与 [mount.rs:52-86](src/kernel/functions/fs/mount.rs) 的挂载检查。`read`、`write`、`unlink`、`socket`、`mmap` 等路径没有等价的检查点。**漏写一处不会让任何审计腿变红**，因为不存在"必须检查"的结构性约束。

**其四，审计链不抗篡改。** 审计哈希用 FNV-1a 64 位串接前序值（[audit.rs:306-320](src/kernel/functions/sgeg/audit.rs)），既无密钥也无签名。任何能写审计区的人都可以重算整条链，链的"连续性"只防误删，不防伪造。

### 其余薄弱面

- **TPM 是软件占位**：8 个 PCR 存在内存数组里（[secure_boot.rs:45](src/kernel/privileged/sgeg/secure_boot.rs)、[secure_boot.rs:347-368](src/kernel/privileged/sgeg/secure_boot.rs)），无硬件根、无密封存储。它可以作为接口形状的预演，不能作为信任根。
- **密码学是混合策略**：SHA-256 自研并带 KAT（[sha256.rs:246-270](src/kernel/privileged/sgeg/sha256.rs)）；常数时间比较自研、以 privileged 为权威（[identity.rs:15-19](src/kernel/privileged/sgeg/identity.rs)）；Ed25519 用 `ed25519-dalek`（[secure_boot.rs:91-100](src/kernel/privileged/sgeg/secure_boot.rs)）；CSPRNG 为 `rdrand` + TSC / 栈地址回退（[csprng.rs:30-58](src/kernel/privileged/sgeg/csprng.rs)）。每一块单独看都有理由，合起来却缺少一份统一的威胁模型——哪些威胁由哪一层承担，没有写清楚。
- **验证面薄**：`kani-harness` 对 SGEG 零引用；host-tests 的权限回归用例以读源码文本、`contains` 断言为主（[fs_permissions_regression_test.rs:167-179](host-tests/tests/fs_permissions_regression_test.rs)、[fs_permissions_regression_test.rs:230-264](host-tests/tests/fs_permissions_regression_test.rs)），是结构锁而非行为验证。
- **存储格式化混入安全子系统**：`SYS_SGEG_DISK_FORMAT` / `SYS_SGEG_DISK_PARTITION` / `SYS_SGEG_FAT_FORMAT` 等臂（[dispatch.rs:1476-1530](src/kernel/functions/syscall/dispatch.rs)）与安全判定无关，属"我需要存储"倒推出来的归属。

### 结构性判断

`Security Guarantee Edgine` 这个名字把**主体身份、访问控制、可信计算**三层职责塞进同一个 syscall 命名空间。后果不是功能少，而是每条能力都停在"想调就调"的层次：调用者必须配合，不配合就没有防线；检查点靠人写，漏写就失效。

由此得到本文的总命题：**把"身份"和"策略"移出内核，把"强制"留在内核。** 内核不认识用户、不认识策略语言，只负责在一次操作上执行一次不可跳过的判定。

## 定位：安全模块，不是安全服务

### 用户裁定

**［用户裁定］** SGEG v2 是**内核安全模块（机制）**，不是安全服务。类比 SELinux：它是内核的一部分，不是"又一个安全 OS 组件"，不提供登录、账户管理、密钥托管之类的服务面。

核心动机来自生态现实：除自写测试程序外，**不会有任何第三方软件调用它，甚至不会知道它存在**。因此它必须"隐身"。

### "隐身"的三层含义

这三层常被混为一谈，必须分开：

| 含义 | 是否做 | 理由 |
|---|---|---|
| **不被调用**（不要求应用配合） | 必须做 | 强制模块存在的意义就是不依赖调用者自觉；靠应用主动上报的机制在生态里等于不存在 |
| **不改变既有语义**（无策略时零差异） | 必须做 | 默认关闭、无策略时行为与无 SGEG 完全一致，是兼容性底线 |
| **完全不可观测** | **不做，且有害** | 故障无法诊断；fail-open 能被接受的前提恰恰是"留下证据" |

正确口径是：**默认不启用、启用后不要求用户态配合、但保留只读内省面**。完全不可观测会把"策略没加载"和"策略加载了但没生效"变成两个无法区分的神秘状态；而一次 fail-open 的启动若没有任何证据，运维只会看到"今天好像不太对"。

### 新增 syscall 数 = 0

**［用户裁定］** SGEG v2 不新增任何 syscall。现有 32 个 `SYS_SGEG_*` 是"为一个不存在的调用者写的接口"，应**整体作废**，不是改造、不是兼容保留。

替代通道全部复用既有语义：

- **策略加载**走"写一个既有路径下的文件"，由用户态策略编译器生成定长表后交给内核；
- **内省**走既有 POSIX 面，例如 `/proc/<pid>/attr/...`、`getxattr`；
- **拒绝留证**写审计记录（落文件或既有日志面）。

这不是暴露 API，是留证。只读内省面与"隐身"不矛盾：正常程序不需要知道它，出问题时运维与审计需要看得到它。

## 形态：内核只保留四个原语

### 四个原语

**［讨论共识］** 内核侧的 SGEG v2 收敛为四个原语，除此之外不做任何策略性工作：

1. **主体标签**：每进程一个，`exec` 时确定，之后不可变（唯一例外是特权重标）。
2. **客体标签**：每文件、目录一个，从父目录派生。
3. **转移规则**：`exec` 时 `(旧标签, 可执行文件标签) → 新标签`；**无规则即继承**，不产生额外语义。
4. **判定**：`(主体标签, 客体标签, 类别, 权限) → 允许/拒绝`。

内核**不认识标签名、不认识权限名、不认识策略语法**，只对编译好的定长表做查表。策略语言、策略编译器、类型名与权限名定义全部在用户态。这一条的工程含义是：内核侧没有解析器、没有求值器、没有正则引擎，也没有可能被策略文本触发的递归或内存分配。

### 一次操作的数据流

```
execve:  (旧域标签, 可执行文件标签) --转移规则--> 新域标签
open:    (域标签, 文件标签, 类别, 权限) --判定表--> Allow / Deny -> fd
read:    只验证 fd（fd 已携带授权，不再逐次判定）
```

判定点在"获得句柄"的那一刻，而不是"每次读写"的那一刻。这个位置选择同时决定了性能模型（见"性能"章）：判定是每次打开一次，不是每字节一次。

### 三条刻意的减法

**［讨论共识］** 三条减法都是主动放弃能力，不是尚未实现：

- **策略语言不在内核。** 没有解析、没有求值、没有正则。内核只吃编译结果。
- **身份不进来。** 账户、密码、登录不进内核（见"身份"章）。
- **可信启动不进来。** 它不是 SGEG 的并列组件，而是 SGEG 能成立的前提：**防 root 提权的前提是存在一个比 root 更高的权威，而这个权威只能来自引导链。** 两者是依赖关系，不是并列关系。把可信启动塞进同一个 syscall 命名空间，会让"模块"看起来像一个什么都管的服务，也会让启动期校验与运行期判定互相掩盖失败。

## 身份：从"拥有身份"到"使用身份"

### 判定输入里不允许出现 uid

**［讨论共识］** 判定输入只允许是域标签，uid 不得作为判定输入。理由很直接：只要 uid 是判定输入，`euid == 0` 就必然在某条路径上短路成放行——这是内核里反复出现的模式，不是实现失误。root 提权于是成为设计的终点，而不是需要防住的目标。

uid 仍然存在，但退化为**普通属性**：用于 `stat` 归属、文件所有权、审计记录、兼容既有程序，不参与"能不能做"的核心判定。主体身份由域标签承担。

### 三条路线

| 路线 | 做法 | 兼容性 | 判断 |
|---|---|---|---|
| **A 标签路线**（SELinux 式） | 内核不管账户，继续用 uid；SGEG 只加标签与判定 | 完全兼容 | **［讨论共识］推荐** |
| B 内核管账户但用 passwd 格式 | 仍需新 syscall 读写账户库 | 破坏"隐身"与"零新增 syscall" | 不推荐 |
| C 独立账户体系（现状 `/pwm.db`） | 内核自带账户库与登录语义 | 与 Linux 二进制兼容性直接冲突 | 淘汰 |

选 A 的推论：**SGEG 不再"拥有"身份，只"使用"身份。** 账户、密码、登录整体搬到用户态——`/etc/passwd` + `/etc/shadow`，由一个 login / PAM 式程序承担。内核只看得到 uid，看不到密码，也不判断"谁是管理员"。

多用户登录这个产品特性不消失，只是不再是内核 syscall。把它做成用户态服务，反而获得了可替换的认证策略（密码、令牌、生物特征）而不触碰 ABI。

### 必须保留的兼容红线

**［讨论共识］** 以下五条是 rebase（跟随 Linux 语义）的硬边界，逐条都有具体后果，不能当作"以后再补"：

- **`setuid` 语义优先于标签转移。** `su`、`sudo`、带 `s` 位的程序依赖"先换凭据再执行"的既有顺序。若标签转移先于凭据变更生效，要么把提权程序锁在旧域里导致功能失效，要么在转移规则里重新打开一条提权路径。
- **`/proc` 既有字段的读法不能变。** 加字段可以，改顺序、改格式、给既有字段加读限制不行——大量程序按固定格式解析 `/proc`，破坏它等于在不相关的地方制造故障。
- **`ptrace` 在允许时必须可用。** 调试器是开发工作流的一部分；一个"安全"到无法调试的内核会让自身无法维护，也会把开发者推向绕过机制。
- **`ld.so` 读库路径不能被策略挡住。** 否则程序在 `main` 之前就失败，错误信息极难懂，用户只会看到"程序起不来"。
- **必须有**无约束默认域**（unconfined）。** 这是 SELinux targeted policy 可用性的来源：绝大多数程序留在默认域，不产生行为差异；只有被明确标记的对象与域进入判定。没有它，默认拒绝会把系统自身先拒绝掉。

## 强制模型：既定部分

**［讨论共识］** 以下四条是已经确定的方向：

- **标签 + 表判定**，不做路径字符串匹配，不做运行时求值。
- **保留 Linux `CAP_*` 不动。** 它是 ABI 的一部分，第三方二进制会查询它。SGEG 在 `CAP_*` 之上**叠加**标签判定，而不是替换。两套机制的交集取严：`CAP_*` 不足则拒绝，标签判定不足也拒绝。
- **默认关闭 + 启用后默认拒绝。** "宽容只记日志"（permissive）可以作为调试档位存在，但不当默认。默认关闭保证不启用时零差异；启用后默认拒绝保证漏配不会静默放行。
- **加载失败走 fail-open + 响亮证据。** fail-closed 会让机器不开机，与"兼容性优先"直接冲突。代价必须诚实写出：**那次启动系统不设防。** 因此失败必须以高可见度留下证据（审计记录 + 内省面可读 + 启动日志），否则 fail-open 就退化成"悄悄没设防"。

三项待定——客体标签粒度、拒绝时的行为、策略所有权——集中在"开放议题"的 OQ-1、OQ-2、OQ-3，此处不预先拍板。

## 触发模型与激活时机

**［讨论共识］** SGEG 是**被动的**：它不拥有任何自己的线程、定时器或轮询，只挂在受保护操作的入口上，跑在调用者的上下文与配额里。这是"隐身"的技术基础——没有独立调度实体，就没有可观测的进程、设备节点或 procfs 入口可供发现；它的运行成本也天然计入调用者，不会凭空产生一个后台负载。

### 钩子内部的三段

一次钩子调用分三段，**只有中间一段算"激活"**：

| 段 | 动作 | 成本量级 |
|---|---|---|
| 分类门 | `(主体类型, 客体类型)` 二维表查一个"有无策略"位 | 纳秒级，常驻 |
| 判定 | 查定长表、验凭据链 | 激活后才发生 |
| 状态更新 | `exec` 换域、`fork` 继承并衰减、`open` 后 fd 带走授权 | 激活后才发生 |

关键区分：**跳变是判定的结果，不是触发条件。** 先有"这次操作要不要判"的分类，才有判定；判定产生标签变化，变化再写回状态。把顺序倒过来，就会得到"先检测跳变、再决定判定"的模型，而那个模型在下一节的两条理由下不成立。

### 为什么不能以"跳变"为触发器

- **累积型攻击不产生跳变。** fork 大量子进程、写满 inode、挤占页缓存，这些行为里标签不变、跳数不变、域不变。若只在跳变时判定，这类攻击的拦截次数是零——而它们恰恰是资源耗尽与拒绝服务的主要形态。
- **识别跳变本身要常驻执行。** 要发现"跳变"，必须在每个操作上比较前后状态；既然常驻比较不可避免，就不如把它做成一次显式的分类门查表。前者是"到处埋检测点"，后者是"一个固定入口"。

### 稀疏性的真正来源

判定并不稀疏，**授权稀疏、使用稠密**：

- 判定发生在**建立引用的时刻**：`open`、`exec`、`mount`、`bind`、`link`、`rename`、`ptrace`、`kill`、`socket`；
- 使用时刻（`read` / `write` 循环、缺页、`mmap` 命中）手里拿的是已带授权的 fd，**fd 即凭据**，不再查表。

这同时是 TOCTOU 的正解：检查与使用之间不存在"再解析一次路径"的窗口，因为使用端拿到的是对象引用/句柄，不是路径字符串。

### 三个必须主动的时刻（都在钩子路径之外）

- **boot / mount**：装载客体标签；
- **策略更新后**：全量重验证，而不是等下一次访问逐条发现失效；
- **exec**：重算主体标签与转移结果。

这三件事不能挂在"某次文件访问"上，因为它们要么发生在任何用户操作之前，要么需要全局视野。

### 自指短路

**SGEG 不得判定自身**，否则一次判定会触发另一次判定，递归没有终点。处理方式是：内核主体域整体豁免，并且**豁免由独立的主体类型在类型层面保证**，不能用一个布尔开关——布尔开关会被误翻，独立类型不会。这与"策略为不可表达非法状态的枚举"是同一条设计规则。

## 性能

> 本章所有数字均为**推算量级，非实测**。它们的用途是判断架构方向是否成立，不是验收指标。

### 第一阶段：标签判定

| 动作 | 推算成本 | 说明 |
|---|---|---|
| 读进程标签 | 1–2 周期 | `exec` 后不可变、无锁、通常 L1 命中 |
| 读文件标签 | 1–3 周期（热）/ I/O（冷） | 缓存在 inode；冷路径要读 xattr，是真实 I/O |
| 查表 | 20–40 周期 | AVC 式 `(主体 × 客体 × 类别)` 哈希缓存，命中率极高 |
| 合计 | 约 10–20 ns | 单次打开 |

相对开销的推算：

- 策略未加载：约 0（一条原子读短路）；
- 真实负载：1–3%；
- `open` 密集型微基准（`find`、包管理器、通配匹配）：5–10%。

原因不是"实现得快"，而是判定位置选对了：**判定是"每次打开一次"，不是"每字节一次"。** 大文件顺序 I/O 的判定开销被摊薄到接近零。

### 两个隐性成本

- **结构体膨胀。** 给进程/文件描述符加标签字段，可能把恰好占满 cache line 的结构挤过边界，带来的代价可能大于查表本身。设计时应把标签打包进既有 padding，而不是新增字段。
- **冷 xattr 路径。** 挂载后首次访问、或 inode 缓存淘汰后重读 xattr，对"扫全盘"类操作是"访问次数 × I/O"的放大。这一项在小基准上看不见，在全盘扫描与包管理器冷启动上会显形。

### 第二阶段：凭据与信任链

每消息附带信任值、接收时 join、设置有效标签，合计约十几 ns / 次 IPC；对 pipe / 微服务密集负载约 5–15%。

**真正的代价不在周期，而在改动面**：所有 IPC 机制（socket、pipe、信号、共享内存、futex）都要携带 provenance 并参与判定，每漏一处就是一条绕过路径。并且"浮动标签"必须作用域化到一次操作——否则守护进程处理过一次不可信请求后就被永久污染，之后它做的每件事都带着被污染的标签。

### 三个便宜的优化

**［讨论共识］** 建议一并写入设计：

- **检查点下沉到 `open`。** fd 天然是授权凭证，大文件 I/O 的开销归零；这与"检查返回凭据而非布尔"的 Rust 设计规则同源。
- **策略重载无锁换代。** 换指针 + 宽限期回收旧表，读路径永不加锁。与 TLB 代（generation）同思路：旧表在宽限期内仍可服务已进入的读者，新读者看到新表。
- **策略未加载用单条原子读短路。** 默认关闭时热路径只多一条原子读，不进入判定函数。

### "类型数 ≤ 256"是性能设计决策

这不是命名洁癖，而是架构约束：类型数若无上界，`(主体 × 客体 × 类别)` 的二维表会爆掉，只能退回"哈希 + 缓存"，命中率与最坏延迟都不可控。把类型数压在 256 以内，表就可以是定长、可预计算、可放进 L1/L2 的结构。**上界换来确定性。**

### 计量从第一天做进去

必须从一开始就采集：判定次数、缓存命中率、拒绝次数、平均周期。理由是：

- 几乎零成本（几个每 CPU 计数器）；
- 它是唯一能回答"到底贵不贵"的依据，而不是靠估算；
- 它同时是用户态策略编译器的输入——编译器需要知道哪些规则被频繁命中，才能优化表的布局。

## 凭据路径与"跳数"

这一章记录本轮讨论里最容易出错、也最有价值的一段推理。它纠正了两个直觉：一是"跳数可以当安全度量"，二是"fork 会让深度增长"。

### 起源与自我纠正

灵感来自 OSPF 的路径代价，但必须立刻纠正：**连 OSPF 自己都放弃了跳数当度量。** 用跳数的是 RIP（上限 15，超过即不可达），OSPF 改用加权代价，因为跳数是坏代理——它把"经过几个路由器"误当成"路径有多好"。所以"最短路径不等于安全"这个判断，与 OSPF 自身的演进方向一致，而不是在反对它。

### 范畴纠正：度量问题 vs 证明问题

**OSPF 是度量问题（标量取最小），安全是证明问题（谓词判成立）。** 两者数学形状不同：

- 度量可以相加、可以比较大小；
- 证明只能验证"这条链是否成立"，不能因为"链短"就认为"更可信"。

一条 1 跳但凭据伪造的路径，比 10 跳但每环可验证的路径危险得多。成熟参照都收敛到同一结论：

- **X.509 证书路径验证**：`pathLenConstraint` 的含义是"长度是上限"，不是"越短排名越高"；
- **委托逻辑（Delegation Logic）**：委托是"权限的子集传递"，不是"距离的累加"；
- **seL4 能力派生树**：派生形成树，权限沿树单调收窄；
- **Macaroon / Biscuit**：caveat 链只做衰减（attenuation），不做加权。

共同结论：**深度是约束条件，不是惩罚项。**

### 必须先拆开的五种"跳"

混用这五种"跳"会直接导致错误的策略：

| 跳的类型 | 含义 | 安全相关性 | SGEG 是否需要 |
|---|---|---|---|
| **拓扑跳** | 目录层级、路径深度 | 几乎无关 | 不需要（OSPF 类比只对这类成立，而这类最无意义） |
| **派生跳** | `fork` / `clone` 产生的代际 | 不构成信任边界 | 不需要计入深度 |
| **调用跳** | A 请求 B 代为操作（混淆代理入口） | 高 | 需要 |
| **委托跳** | 真正的凭据链：A 把权限授予 B | 高 | 需要 |
| **数据跳** | 信息流：数据从高密级流向低密级 | 高，但属信息流模型 | 远期，不在第一阶段 |

SGEG 真正需要建模的是**调用跳与委托跳**。把目录深度或 fork 代数算进"跳数"，是在度量一个与安全无关的量。

### 严谨核心三条

**［讨论共识］**

1. **每跳只能收窄，不能扩张。** 衰减（attenuation）/ 权限掩码（rights mask）/ caveat 单调性。seL4 的 rights mask、Macaroon 的 caveat、Biscuit 的链，三套独立演化的系统都收敛到这一条——因为缺了它，任何链式委托都会在某一跳放大权限。
2. **验证在授予时，不在使用时。** 每次 `open` 逐跳验签是 O(深度)，而深度没有上界，热路径会崩。正确做法是：授予时校验整条链，把它坍缩成一个不可伪造的内核句柄；使用时只验句柄。这与 fd 的模型完全相同。
3. **深度是上限 + 撤销时效，不是扣分项。** 深度用于限制"最多能跨几层"，撤销时效用于限制"旧授权还能活多久"；两者都不是"跳数越多越可疑"的评分。

### 必须堵的漏洞：权限放大的传递闭包

A 能授予 B 读，B 能授予 C 读，则 A 实际上间接授予了 C 读——即使 A 无权直接给 C。这是委托模型的经典放大问题，三个堵法按实现简单度排序：

1. **默认不可再委托**：授权句柄带 no-delegation 位，B 拿到后不能转手；
2. **深度上限设很小**（例如 2）：用上限截断闭包，代价是复杂委托场景做不了；
3. **只有被明确授权的域可再委托，且只能给真子集**：表达力最强，但需要证明"子集"关系，复杂度上升。

### 建议：先做 1 + 2，深度设为 1

**［待定］（AI 建议，用户尚未裁定）** 第一版只做"授予时验证 + 不可再委托"，委托深度设 1——只有一层，B 拿到后不能继续授予。

理由：这已覆盖"守护进程替客户端做事"这一最主流场景，而它正是 root 提权的主要入口（客户端让 root 守护进程代为打开文件）。完整委托逻辑（证明搜索、Datalog 求值）不简单，会渗进策略编写、诊断工具、性能分析每一层，与"简单且实用"直接冲突。

这条建议的代价是：多级服务链（客户端 → 代理 → 后端 → 存储）在第二层就会被截断，需要合并为单层代理或由策略显式放行。是否接受这个限制，需要用户裁定。

### `fork` 不是委托，跳数不随 `fork` 增长

**［讨论共识］** 子进程继承的是**父标签本身**，不是"父标签 + 1"。同一棵进程树里，每个节点离原点的信任距离相同。若按 fork 递增深度，会精确制造病态：`make -j64` 拉起几百个进程、构建树深 5 层，会被判"跳数超限拒绝"——安全上什么都没防住，正常业务全废。

跳数只计三类事件：**跨信任边界的权限授予、`execve` 上的标签转换、请求代理**。不计 `fork` / `clone`、同域函数调用、目录层级。

一句话概括：**深度衡量横向跨越了多少条信任边界，不是纵向生了几代。**

### 深度与宽度是两件事

**［讨论共识］** 委托是**乘性**的：A → B → C，每一跳都可能放大权限，所以要限深度。分叉是**加性**的：父进程给 1000 个子进程同样的权限，是 1000 份独立、可验证的授权，没有任何一个子进程因此获得父进程没有的权限。

**分叉放大影响面，不放大权限面。** 把两者混进同一个"跳数"计数器，会既挡不住真正的放大，又误伤正常并发。

### fork 炸弹：不是安全判定，是资源问题

**［讨论共识］** fork 炸弹是 DoS，不是访问控制。"复杂程序"与"炸弹"没有任何静态属性可区分：进程数、树形、标签都一样，唯一区别是速率与生命周期分布——而这两者是运行时统计量，不是策略谓词。

正确归属是资源配额 / 记账，不是策略引擎。SGEG 在这里只有三处正当位置：

1. **谁能 fork / exec**（安全判定）；
2. **子进程继承什么标签**（安全判定）；
3. **资源耗尽时优先牺牲谁**（策略关心资源，但决定"谁死"，不决定"多少算多"）。

记账本身归资源层。接口应当是资源层触顶时**询问**策略"这个域能否使用该额度"，而不是 SGEG 自己去数进程。可以把"某域极短时间内大量 fork"记为**审计异常信号**（可能被攻破、可能配置错误、也可能真是炸弹），但**不触发访问拒绝**。

### 客体侧可以静态化

这一条纠正了更早的悲观估计。客体侧的距离是**静态属性**：只在 `mkdir` / `rename` / `link` / `mount` 这类结构性操作时变化，比 `open` / `read` / `write` 少几个数量级。因此可以：

- 加载时预计算；
- 结构变更时按子树失效；
- 热路径只读缓存字段。

进一步，距离取值有限（例如 0–7），`(类型, 距离)` 可以在用户态策略编译器里**全展开成一张表**，内核运行时只有一次查表，无图遍历、无循环。还可以把 `(type_id, depth)` 打包进一个 `u32`（高位类型、低 3 位深度），查表仍是二维，join 仍是 min/max，不增加结构。

**主体侧的 provenance 是动态的，只能逐条携带，这部分绕不过去。** 不要把客体侧的静态化成功误推为主体侧也能预计算。

### 跳数是判定表字段，不是触发器

**［讨论共识］** 跳数不是触发 SGEG 的条件，而是判定表的一个输入字段：`(主体类型, 客体类型, 操作, 跳数档)`。它只在**主体标签变更**或**客体移动**（`mkdir` / `rename` / `link` / `mount`）时重算，热路径读缓存字段。把它当触发器，会退回到"跳变驱动"的模型，而那个模型已被"累积型攻击不产生跳变"证否。

## 多判据组合模型

**［讨论共识］** 单一判据的系统有结构性缺陷：**一个判据被绕过，整体失效。** 更具体地说，跳数的回答域天生有限——它只回答"这条授权能不能到这儿"，回答不了"到了之后能干什么"，也回答不了"到了之后干了多少"。把后两个问题硬塞给跳数，会让它承担一个它无法承担的语义。

### 统一判定接口

判定收敛为一个接口：

```
decide(subject, object, op, ctx) -> Verdict
```

`ctx` 是一组**证据**，每条证据由一个独立判定器产生；跳数与纪元从此降级为其中两项，而不是接口本身。这样做的工程价值是：**加判据不改调用点，也不改策略表格式。** 新判据只是 `ctx` 里多一项证据，调用方与策略编译器不需要跟着变形。

### 组合必须合取，不得加权打分

**［讨论共识］** 所有判据全部通过才允许。三条理由：

- **加权不可证明。** 无法论证"85 分等于安全"——阈值是拍出来的，不是推出来的，任何证明都只能覆盖单个判据。
- **可被优化攻击。** 攻击者不必绕过任何判据，只需把总分压在阈值以下：每个判据都"差点拦住"，合起来全部放行。合取没有这个面。
- **MAC 的数学基础是格，不是分数。** Bell-LaPadula 是偏序关系；引入实数权重会丢掉传递性与单调性，判定结果不再能沿格结构推理。

合取还有一个增量性质：**新判据只会让系统更严，不会让已有保证变松。** 这是安全机制可增量演进的唯一形式——每加一层，旧的证明仍然成立。

### 四个候选判据

| 判据 | 防什么 | 成本 |
|---|---|---|
| **配额** | 累积型行为：fork 炸弹、写满 inode、挤占页缓存 | 一次计数器比较 |
| **速率** | 暴力猜测、目录扫描、syscall 洪水 | 一次整数运算（令牌桶或 EWMA） |
| **序列** | 单步都合法、组合成攻击（例如读 `~/.ssh` 后若干步内外联） | 一次状态转移，需存状态 |
| **信息流** | 合法读取之后的非法外泄 | 最贵：需在写入侧传播标记（格 + 污点） |

四者的共同点是都能回答跳数回答不了的问题：配额回答"干了多少"，速率回答"多快"，序列回答"先后组合"，信息流回答"数据去了哪"。

### 三类明确不归 SGEG

- **时序与侧信道**：归调度与架构（缓存分区、常量时间、抢占策略）。
- **完整性度量**：归 `secure_boot` 那条线（见"边界"章的供应链植入）。
- **真正意义上的入侵检测**：归审计与行为基线。

理由一致：把这些塞进判定器只会拉长判定路径，让"简单"失守。判定器每多一个分支，热路径的可证明性与可测性就少一分。

### 边界精确化：SGEG 判额度，策略表判权限

**［讨论共识］** 前文说"fork 炸弹不归 SGEG"，精确含义是：**不该由策略表判"允不允许 fork"**——那是权限问题，答案是"能"或"不能"，与进程数量无关。而"该主体已经用掉多少"是 O(1) 计数器可以回答的，且 SGEG 恰好持有**可信的主体身份**，这是别的层拿不到的输入。

`cgroup.rs` 的 `try_charge` / `check_budget` 是一个恰当的反例：原语已经存在，但全仓没有调用者把它们接到 fork 与内存分配路径（见"落地约束"）。配额判定器的价值不在新写记账代码，而在**把既有原语接进判定路径，并赋予它可信的主体身份**。

### 分层短路

判据按"成本 × 失败概率"排序，任一层拒绝即返回：

| 层 | 内容 | 成本 | 覆盖面 |
|---|---|---|---|
| **L1 静态表** | 定长表查表，含跳数档 | O(1) | 绝大多数操作死在这一层 |
| **L2 动态证据** | 配额、速率、纪元，均为字段比较 | O(1) | 累积型与时效型行为 |
| **L3 有状态判据** | 序列、信息流 | 需存状态 | 只对被标注的主体或客体启用；未标注不进该层，成本为零 |

分层的意义不是"更快"，而是**让最贵的判据只作用在最小的集合上**。L3 如果全局启用，等于把内核变成一个有状态分析器；靠"标注"开关把它限制在少数域，成本才可控。

### 第一阶段只做三条 O(1) 判据

第一阶段实现**跳数、纪元、配额**：三条都是无状态或单计数器，可证明、可测、可穷举。序列与信息流留到第二阶段，启用方式是"标注"开关，不是全局开关。这样第一阶段的判定路径长度是常数，性能模型（见"性能"章）仍然成立。

## 授权时效：失效纪元

**［讨论共识］** 跳数与凭据链只能回答"这次授权传递是否合理"，回答不了"这份授权现在是否还应该有效"。一个攻击者可以走在一条**每个维度都完美**的路径上：凭据完整、每跳收窄、跳数很小，但它持有的授权可能早在很久之前就该被撤销。

失效纪元（revocation epoch）作为第二判据：

- 主体标签降级时（例如从高信任域降到低信任域），递增该主体的纪元号；
- 已发出的凭据携带**签发时的纪元**；
- 使用时刻只比较一个整数：凭据纪元等于当前纪元才有效，否则凭据失效。

代价与收益必须一起写：

- **代价**：一次降权需要扫一遍在途凭据（或按纪元批量作废），这是一次冷路径的全局动作；
- **收益**：稠密路径仍然只有一次整数比较，既优于"每次 `read` 重新判定"，也优于"授权一次、永久有效"这两个极端。

它和跳数是互补的：跳数管"横向跨了几条信任边界"，纪元管"纵向过期了没有"。具体粒度与在途凭据的清扫方式见 OQ-8。

## Rust 特性：真实优势与蒸发处

这一章区分"生命周期"与"类型系统"两类优势。它们不是"用了 Rust 就自动获得"，而是"按 Rust 的形状设计 API 才获得"。

### 生命周期带来的三条真实优势

1. **作用域化的临时标签。** 浮动标签在 Rust 里是持有 `&mut` 的 guard，出作用域必然恢复，早返回也恢复。C 里是 save / restore 配对，真实 bug 几乎全是某条 `goto out` 漏了 restore——Linux 最后用 `__attribute__((cleanup))` 补，等于在 C 里手搓 RAII。
2. **"检查后使用"不可拆开（TOCTOU）。** C 的经典提权原语是 `access()` 之后 `open()`：两次解析路径，中间可被替换。若检查返回的是**到对象的引用**而非布尔，就不存在"再解析一次"，检查与使用被类型系统焊在一起。这类 CVE 反复出现不是"写错了"，是 C 的 API 形状允许"写对检查、写错使用"。
3. **能力靠所有权表达。** `File` 拥有权限，`&File` 即能力，没有 `&File` 写不出 `read`。这就是 Capsicum 模型，但不需要新 API，因为它是 Rust 的默认形状。

### 类型系统带来的优势

单独列，避免与生命周期混为一谈：

- **newtype 严格区分** `SubjectLabel` / `ObjectLabel` / `TrustLevel`，防止把主体标签当客体标签传；
- **sealed / 私有字段**使标签不可伪造，构造器只在 TCB 侧；
- **策略解析成枚举**后"非法状态不可表达"，校验一次在加载，热路径无条件信任形状；
- **`#[must_use]`** 让忽略拒绝成为告警；
- **`#![forbid(unsafe_code)]`** 使策略引擎自身不可能被内存破坏。

### 最大的一项：漏检查变成编译错误

检查器返回只能由它构造的 **Witness**，`open` / `read` / `unlink` 的签名要求 `&Witness`，未通过检查的调用**编译不过**。

这一条正对症：当前靠审计脚本盯"编号已声明但未接线"，是用工具补语言的短板；而 `functions/` 有几百个文件且持续新增 syscall，靠人盯和脚本迟早会漏。把"必须检查"抬到类型层，是把防线从"事后扫描"改成"事前不可写"。

### 优势蒸发处

必须写清楚，否则会高估 Rust 的作用：

- **`panic = "abort"` 下 Drop 不执行。** guard 只在正常路径成立，panic 路径上恢复动作不发生，需要第二道保险（例如显式恢复点或独立的状态重置），不能把 RAII 当作唯一保证。
- **内核里很少拿得到 `&mut`。** 共享状态通常在 `IrqSpinLock` 后面，借用检查器**看不懂锁保证了互斥**，编译期不再证明"同一时刻只有一个修改者"。锁纪律仍然要靠审计与约定。
- **保证在 TCB 边界终止。** `privileged/` 的 `unsafe` 会把引用擦成裸指针或 `&'static`；buffer 被释放重建后，安全层仍持旧引用即 UAF，编译器不会报警。这正是 FREG 的核心问题，**Rust 救不了经 `unsafe` 逃逸的引用**，所以必须 `Handle + gen`。SGEG 同理：客体标签挂在 inode 上，inode 被换出、重建、复用后旧句柄必须被拒。
- **用户输入永远是未验证整数。** 生命周期对"这个 `u64` 是不是有效 fd"毫无帮助，边界校验仍要显式做。

一句话：**Rust 消掉了编译器可见的那部分 UAF，消不掉穿过 `unsafe` 的那部分。**

### 四条设计规则

**［讨论共识］** 优势不是"用了 Rust 就有"，是按 Rust 形状设计 API 才有：

1. **检查返回凭据，而不是布尔。** 返回 `Witness` / 句柄，调用处不可能"检查过但用另一个对象"。
2. **VFS 操作接受"拥有权限的对象"，而不是路径。** 路径是字符串，可以重解析；对象是引用，检查与使用同源。
3. **标签类型严格分离，构造器只在 TCB 侧。** functions 层不能凭空造一个"已授权"标签。
4. **策略加载后是"不可表达非法状态"的枚举。** 加载时校验一次，热路径不再做防御性判断。

并主动放弃一条幻想：**不要指望生命周期替管跨边界对象的寿命。** 凡可能被重建的对象（inode、capsule、socket）统一用代号句柄——这不是 Rust 的退让，是任何内核都必须做的事。

## 落地约束：被外部子系统卡住的排期

### 标签的存储依赖文件系统

标签原则上存在 xattr 里，而 xattr 是文件系统能力。现状比"没有 xattr"更微妙：接口存在，但**无法承载标签字节**——EGFS 的 `setxattr` 只接受 4 个名字槽位，并把值压缩成一个 `u64` 哈希存进 `data_hash`（[egfs_data.rs:1257-1270](src/kernel/functions/fs/egfs/egfs_data.rs)），`getxattr` 返回的是这个哈希的 8 字节（[egfs_data.rs:1300-1308](src/kernel/functions/fs/egfs/egfs_data.rs)），原始值不可还原。用它存标签，读回来的是标签名的哈希，不是标签本身。

同时文件系统的崩溃一致性尚未闭环：`zil.sync` 只清内存记录，磁盘 WAL 实现 `zil_persist.rs` 在内核侧零调用者、挂载路径从不重放日志（[subsystem-gap-deep-audit.md](docs/report/subsystem-gap-deep-audit.md)）。

结论：**SGEG v2 的落地被文件系统卡在后面。** 设计可以先做，"能跑起来"要等 EGFS 具备可持久化、可崩溃恢复的 xattr。这是排期问题，不是理论问题。替代方案（把标签放独立元数据文件或侧表）会引入新的持久化一致性问题，不应作为默认路径。

### 资源记账：机制在，接线断

记账原语并非完全不存在：`privileged/proc/cgroup.rs` 已有 `try_charge` / `check_budget`，也有 `cgroupfs` 面。但全仓没有调用者把它们接到 fork、内存分配或调度路径上——与 `/pwm.db` 是同一类问题：机制在、接线断。

因此 fork 炸弹类问题**现在不是"SGEG 判错"，是"没有地方判"**。缺的是 OOM 分级、按域的优先牺牲裁决，以及"资源层触顶时询问策略"的接口。这属需单独立项的缺口，不应塞进 SGEG 的判定表里凑数。

## 边界：SGEG 不解决的攻击类型

把"内部攻击"当成一个整体，是设计上最常见的偷懒。它至少分四类，SGEG 对每一类的答案不同。

### 恶意用户态程序 ［讨论共识］

**有解，但解不是"收缩权限"，而是"域分离"。**

- 限制 syscall 只在程序无法提权时有用：一旦它拿到 root，限制清单本身就可以被它改写或绕过，防线归零。
- 把它关进一个只能访问自身数据的域，损失才有界：即使完全被控制，它能破坏的也只是自己的数据与自己的配额。
- 代价是**必须为关键域预置策略**。而 Edgine 没有发行版、没有打包体系、没有维护 refpolicy 的人力，因此只能走"**默认宽、少数关键域收紧**"，不能走"默认严 + 白名单"——后者的运维成本会先于安全收益压垮项目。

**［讨论共识］** 这条路线成立的前提是承认"默认宽"：绝大多数程序留在无约束默认域，只有身份、网络、存储等少数关键域进入判定。关键域清单本身见 OQ-9。

### 供应链植入 ［讨论共识］

**几乎无解。** 对 SGEG 来说，被植入的程序执行的是合法的 `exec`、携带完整的凭据、跳数也合理——它在判定表的每一个维度上都"正确"。这类攻击只能靠完整性度量（签名、度量日志、远程证明）与系统外防线（构建可复现、制品签名、发布审计）。

现状必须写明：`secure_boot.rs` 的 `verify_image` 只有一个 `EG_SECURE_BOOT` syscall 入口（[types.rs:850](src/kernel/privileged/syscall/types.rs)、[dispatch.rs:293-296](src/kernel/privileged/syscall/dispatch.rs)），且平台密钥全零初始化（[mod.rs:66-72](src/kernel/privileged/sgeg/mod.rs)）。这一层目前是空壳，属**独立缺口**，不是 SGEG 的职责——把它塞进运行时策略只会制造"看起来验过了"的假象。

### 内核内后门 ［讨论共识］

**答案在架构，不在运行时策略。** Framekernel 的 `privileged/` 与 `functions/` 分界、`#![deny(unsafe_code)]`、依赖单向、审计脚本，共同把"可作恶代码"收缩到一小块可审查的 TCB。结构性隔离强于运行时判定：一段已经在 ring 0 里、且能改页表的代码，任何策略表都拦不住它。

因此 SGEG 不应试图覆盖这一类。声称"安全模块能防内核后门"的机制，通常只是把后门挪到了策略引擎里。

### 被劫持的合法进程 ［讨论共识］

**这是 SGEG 的主场，也是相对 SELinux 的唯一差异化。** SELinux 的类型转换是静态的：它知道"哪个域在发请求"，但不知道"这个请求代表谁发出"。一个被攻破的浏览器让 root 守护进程代为打开文件时，守护进程的域是合法的、凭据是完整的、跳数是合理的——静态 MAC 在这里没有可判的东西。

凭据链解决的正是混淆代理：请求携带的是"谁委托、委托了什么、衰减到什么程度"，而不是只有"发起者的域"。这也是第二阶段（OQ-4）的价值所在。

### 定位：损害面收敛，不是检测

**［讨论共识］** SGEG 对内部攻击的作用是**损害面收敛（containment）**，不是**检测（detection）**。

病毒与后门的共性是**以合法身份运行**。MAC 的哲学是不看意图、只看能力：它能防越界（这个域不能读那个对象），防不了界内破坏（这个域在自己的数据里做什么）。检测需要完整性度量、行为基线、异常检测等另一套机制，与判定表不是同一个东西。

因此必须有一节明确写出"SGEG 不解决什么"——否则每一次没防住都会被读成"模块有 bug"，而不是"这不在它的能力范围"。

### 隐身与可观测性的张力 ［讨论共识］

用户态看不到 SGEG，意味着用户态也无法通过它做审计告警——这是"完全不可观测"路线的真实代价。解法不是把接口暴露出去，而是：

- **审计出口收在内核侧**，单向写入；
- 通道只有特权主体可读，普通程序既看不到接口，也看不到结构；
- 只暴露**结论**（谁在何时被拒、命中哪条规则、是否 fail-open），不暴露策略表与标签布局。

这样既不破坏"不要求应用配合"，也让故障与攻击留下可读的证据。通道形态与"特权主体"的界定见 OQ-7。

### 网络边界：为什么不做防火墙 ［讨论共识］

两个问题本质不同：防火墙回答"**这个包该不该进出**"，SGEG 回答"**这个进程该不该开这个口子**"。前者是流级别的策略，后者是主体—客体级别的判定，输入、频次与信任假设都不同。

**三条硬性不匹配。**

- **频次。** MAC 是稀疏的：建引用时刻判定一次（`open`、`connect`、`exec`）；包过滤是稠密的：每包一次，百万 pps 是常态。合并会把判定路径推进软中断与 NAPI 上下文，而 SGEG 的前提是跑在调用者上下文、可阻塞、可审计、失败可返回错误码——中断上下文里这三条全不成立。
- **状态。** SGEG 的判定是无状态纯函数（主体、客体、操作、证据 → 判定），这是它能被缓存、被穷举测试、被形式化论证的根本；防火墙需要连接跟踪状态机（TCP 状态、分片重组、序列窗口），一旦引入流状态，纯函数性质作废，可证明性的论述随之失效。
- **信任边界。** 包过滤的输入是不可信数据，需要在内核解析协议头、处理分片重叠与 IP 选项，这是内核漏洞最集中的区域；让 TCB 内的 SGEG 解析攻击者构造的字节，等于把最大攻击面接到安全模块上。SGEG 的输入必须是内核已经结构化好的事实，不能是原始字节。

**网络攻击五类及归属。**

| 攻击类型 | 归属 |
|---|---|
| 协议栈实现漏洞 | 减少攻击面 + 域隔离；SGEG 的作用仅限**事后横向移动受限**——网络栈被攻破后仍只是一个只能碰网卡缓冲与有限队列的域 |
| 服务层 RCE | 落入内部攻击第 1、4 类，靠域分离与凭据链 |
| 未授权暴露 / 端口意外监听 | 默认策略问题：默认不监听、默认拒绝入站；执行机制不是包过滤 |
| 洪泛与 DDoS | 速率判据与配额挡内生部分；真正防线在网卡与上游 |
| 凭据窃取与中间人 | 归加密与密钥管理；SGEG 只保护"谁能读密钥客体" |

**SGEG 在网络边界的四个正确位置。**

这四处都稀疏，都落在"建引用时刻"：

- **`connect` / `bind` / `accept` 的命名判定**：谁能连哪、谁能监听哪个端口；
- **socket 作为客体带标签**：对端地址与协议足以映射出"外部不可信"这类标签；
- **`SCM_RIGHTS` 传递判定**：把已授权 fd 递给另一域，是典型的混淆代理渠道，不判等于敞开的后门；
- **网络栈本身作为一个域**：只给网卡与缓冲，不给文件系统——"域分离优于权限收缩"的教科书案例。

**socket 标签接入多判据模型。**

socket 带标签之后，网络自动接入上一章的判据集合：从"外部不可信" socket 读到的数据写入内部客体，正是 L3 信息流判据的输入。**网络不需要单独一套安全机制，它是这套判据的一个客体来源。**

**架构收口。**

不新建"防火墙"概念，SGEG 也不长出包过滤分支。内核侧只保留两件事：

1. 网络域**默认拒绝入站**；
2. `域 → 可否 bind 端口 X / connect 地址 Y` 的判定，数据来自策略表，由网络子系统调用 SGEG 查询，**不反向依赖**。

复杂的连接级策略放用户态自由组装。内核只回答稀疏的、可以用结构化事实表达的那一部分。

**未核实项。**

**［待定］** Edgine 网络栈当前的实现程度、socket 层是否已有独立的客体抽象，均**未核实**。若没有，"socket 带标签"不是加个字段，而是一次结构性改造。这一点不得写成既存事实；需要核实的对象见 OQ-10。

## 开放议题

以下保留全部 OQ 编号：未闭合项标 **［待定］**，已闭合项标 **［用户裁定］**；未闭合项逐条给出待定原因、备选与代价，已闭合项给出结论与理由。编号不重排，便于与既有讨论对照。

### OQ-1 客体标签粒度 ［待定］

**待定原因。** 粒度决定安全覆盖面，也决定与 Linux 语义冲突的面积。文件/目录有现成的 xattr 挂载点；socket、共享内存、pipe 没有 xattr，需要内存侧表，且要与对象生命周期耦合（对象重建后旧标签必须失效）。粒度越细，判定点越多，绕过路径也越多。

**备选与代价。**

| 备选 | 覆盖 | 代价 |
|---|---|---|
| A 仅文件 / 目录 | 持久对象 | 最简单，与 xattr 同构；IPC 面完全无覆盖，混淆代理只能靠主体侧凭据补 |
| B A + socket / 共享内存 / 进程间通道 | 持久对象 + IPC | 需要内存侧表与 `Handle + gen`；判定点扩展到全部 IPC，改动面大，漏一处即绕过 |
| C 全部内核对象 | 最大 | 需要完整对象模型，与 fd 对象模型设计强耦合；实现与验证成本最高 |

### OQ-2 拒绝时的行为 ［待定］

**待定原因。** 只返 `EACCES` 兼容性好，但攻击者可以反复探测、程序可以静默回退到不安全路径；同时终止进程更安全，但误报会杀掉构建工具、守护进程与交互式程序，且故障定位更难。

**备选与代价。**

| 备选 | 行为 | 代价 |
|---|---|---|
| A 仅 `EACCES` | 兼容 | 允许探测与回退；老程序能继续跑，但绕过面留存 |
| B 拒绝即终止进程 | 强 | 误报代价高；需要成熟的调试档与审计，否则运维不可用 |
| C 按域配置（策略决定） | 灵活 | 引入策略表达力与"谁配谁"的所有权问题，复杂度上升 |
| D `EACCES` + 审计 + 速率限制 | 折中 | 不阻断探测但留下证据；限流本身需资源记账支持 |

### OQ-3 策略的所有权 ［待定］

**待定原因。** 若任何 root 进程都能加载或替换策略，整套机制对 root 提权无效——攻击者先换策略再提权。但限制过严则无法运维：升级、回滚、灰度都需要改策略。

**备选与代价。**

| 备选 | 谁能改 | 代价 |
|---|---|---|
| A 任意 root | 简单 | 对 root 提权无效，机制失去意义 |
| B 仅签名策略 | 持签名密钥者 | 需要密钥管理与离线签名流程；持有密钥的 root 仍可换策略 |
| C 启动期固定，改策略需重启 | 引导链 | 最强，但运维成本高，无法灰度 |
| D 启动期基线 + 运行时签名的增量 | 分层 | 表达力与安全性兼顾，实现与验证最复杂 |

策略所有权与可信启动是同一问题的两面：**没有引导链提供的更高权威，运行期的"仅签名策略"仍然可以被 root 替换掉验证公钥。**

### OQ-4 第二阶段（provenance / 信任链）是否做、何时做 ［待定］

**待定原因。** 它是防混淆代理与守护进程提权的唯一手段，但代价是全部 IPC 机制都要携带 provenance 并参与判定，且浮动标签必须严格作用域化。当前生态里没有第三方调用者，投入产出比在短期内不明显；但不做，第一阶段只能挡住直接文件访问，挡不住"让 root 守护进程替我做"。

**备选与代价。**

| 备选 | 时机 | 代价 |
|---|---|---|
| A 不做 | 永不 | 接受混淆代理风险；第一阶段价值仍在，但 root 提权入口未闭合 |
| B 第一阶段稳定 + EGFS xattr 达标后做 | 中期 | 依赖顺序清晰；期间存在已知缺口，需在文档与审计中明示 |
| C 与第一阶段同批做 | 立即 | 改动面最大，验证成本最高，且对象模型（OQ-1）未定前无法收敛 |

### OQ-5 文件名是否带版本后缀 ［用户裁定 · 已闭合］

**［用户裁定］** 文件名不带版本后缀，定为 `docs/design/sgeg-design.md`；版本信息（本文描述的是 SGEG v2）只由正文承载，不进文件名。

理由：

- 与 `freg-design.md` 的命名一致，设计文档族保持同一种形态；
- 文件名带版本会让后续版本无处安放——同一份设计应随演进直接改正文本体，而不是并列堆放 `*-v2`、`*-v3` 等互不统属的快照。

本条已闭合，不再作为待定项；OQ 编号保留，以免重排后与既有讨论记录对不上。

### OQ-6 现有 32 条 syscall 的逐条处置 ［待定］

**待定原因。** "整体作废"是方向（［用户裁定］），但逐条归类仍需清单：哪些直接删除、哪些转用户态、哪些并入既有 syscall 语义。删除前还要核对调用者：`src/user/lib/src/sys.rs` 仍有 18 处 `SYS_SGEG_*` 引用，测试程序与文档也可能依赖。

**备选与代价。**

| 备选 | 做法 | 代价 |
|---|---|---|
| A 一次性全部删除 | 快 | 需同步清理用户态库、测试与文档；遗漏会造成编译失败或运行期 `ENOSYS` |
| B 分三批（身份 → 用户态；存储 → 存储层；杂项 → 既有 syscall） | 稳 | 需要批次追踪与过渡期兼容说明，周期较长 |
| C 保留编号但恒返 `ENOSYS` | 墓碑 | 防止编号被误复用；但死面留存，与"整体作废"的语义不符，也增加审计噪音 |

### OQ-7 审计出口的形态与"特权主体"的界定 ［待定］

**待定原因。** "隐身"要求不暴露接口，"留证"要求可读，两者需要一个精确的交点，而"只有特权主体可读"里的特权主体尚未定义。若用 `uid == 0`，则 root 提权后既能读也能改审计；若用域标签，则产生依赖环——审计者需要先被策略标注，而策略加载失败时恰恰最需要审计。通道形态（procfs 节点、内核环形缓冲、独立设备节点）还决定它能否单向、能否抗篡改、能否被普通程序发现。

**备选与代价。**

| 备选 | 形态 | 代价 |
|---|---|---|
| A `/proc` 只读节点 | 复用既有 POSIX 面 | 兼容、实现简单；procfs 可见即部分暴露，且读权限只能靠 uid 粗分 |
| B 特权域专用的内核环形缓冲 + 一次性拷出 | 不暴露结构 | 最符合"只暴露结论"；需要新的读取路径或复用既有日志面，验证成本中等 |
| C 独立审计设备节点 | 类似 `/dev/kmsg` | 可见性最高、工具最成熟；与"隐身"冲突最大，且设备节点本身成为攻击面 |

### OQ-8 失效纪元的粒度与在途凭据清扫 ［待定］

**待定原因。** 纪元要解决"授权过期"，但粒度选择直接决定误伤面与实现复杂度。全局纪元最简单，却会让一次降权作废所有域的全部凭据；每主体纪元更精确，但凭据需要携带主体标识与纪元，且"标签降级沿进程树传播"的规则必须先定义。在途凭据数量没有上界，全量清扫的成本也不可控；此外还要处理纪元回绕。

**备选与代价。**

| 备选 | 粒度 | 代价 |
|---|---|---|
| A 全局纪元（32/64 位） | 全系统 | 实现最简、比较最便宜；一次降权误伤全部域，且无法区分"谁该失效" |
| B 每主体纪元 | 每个域 | 精确、误伤小；凭据结构变大，需要定义降级传播与子域纪元继承 |
| C 每凭据过期时间 | 每条授权 | 理论上无需扫描；依赖时钟可信度，而时钟本身可被攻击面影响，且无法表达"立即全部作废" |

### OQ-9 "关键域"清单与维护归属 ［待定］

**待定原因。** "默认宽、少数关键域收紧"已达成共识，但哪些域算关键域没有裁定。清单过短则保护不足，过长则回到 refpolicy 的运维成本，与"无发行版、无打包体系、无维护人力"的现实冲突。清单还需要随系统演进而维护，维护者归属未定。

**备选与代价。**

| 备选 | 范围 | 代价 |
|---|---|---|
| A 最小集：身份/认证、网络入口、存储格式化 | 3 类左右 | 最易维护、误伤最小；覆盖窄，守护进程类提权入口可能漏在外 |
| B 中集：A + 设备管理、模块加载、时间 | 6 类左右 | 覆盖提升；每类都需要策略作者与回归测试，维护成本明显上升 |
| C 内核不内置清单，由策略发行方决定 | 外部定义 | 内核保持最小；但默认交付没有可用策略，"启用即默认拒绝"会先拒绝系统自身 |

### OQ-10 socket 客体标签的粒度与网络栈改造范围 ［待定］

**待定原因。** 直接原因是**网络栈现状未核实**：`functions/net/` 的 socket 是否已有独立客体抽象、`privileged/net/` 是否有可挂标签的位置、fd 到 socket 的映射是否已有句柄与代号，均未确认。若没有，这不是加字段，而是结构性改造。其次是 socket 没有 xattr，标签只能放在内存侧表，需要与对象生命周期耦合（重建、复用后旧标签必须失效）。粒度还决定覆盖与语义冲突的面积。

**备选与代价。**

| 备选 | 做法 | 代价 |
|---|---|---|
| A 创建时打"外部 / 内部"单一标签 | 最简 | 实现最小、判定最便宜；无法区分回环、局域网、互联网，所有外部对端同一标签，策略表达力最弱 |
| B 按对端地址段细分 | 地址段 → 标签映射 | 更精确；需要地址空间与策略表的映射，IPv6、NAT、地址漂移都要处理，策略维护成本上升 |
| C 引入连接级标签 | 每连接一个标签 | 覆盖最强；需要连接跟踪状态，与"判定是无状态纯函数"的性质冲突，也把网络栈状态拖进判定路径 |

核实对象：socket 对象模型与生命周期、fd 身份是否可用 `Handle + gen`、网络子系统与 SGEG 的调用方向是否允许"网络问策略"而不反向依赖。

### OQ-11 L3 有状态判据的启用粒度 ［待定］

**待定原因。** L3（序列、信息流）只在被标注的主体或客体上启用，未标注不进该层、成本为零——这一点已达成共识。但"标注谁"没有裁定：按主体标注只能约束被审查的域，客体未标注则信息流找不到汇点；按客体标注能保护敏感数据，但源未标注时污点无法传播；双向标注最完整，但策略编写量最大。粒度还决定 L3 状态表的规模与淘汰策略。

**备选与代价。**

| 备选 | 标注对象 | 代价 |
|---|---|---|
| A 按主体标注 | 域 | 实现简单、per-process 状态好管理；客体侧无标签时信息流判据退化为序列判据，外泄汇点无法识别 |
| B 按客体标注 | 文件 / socket 等 | 能直接保护敏感客体；源侧未标注时无法判断污点来源，序列判据也缺少主体身份 |
| C 主体 + 客体双向标注 | 两侧 | 判据完整、可表达真实信息流；策略编写与维护成本最高，标注遗漏会直接变成绕过路径 |

### 已定决策汇总

- **［用户裁定］定位**：内核安全模块 / 机制，不是安全服务；类比 SELinux。
- **［用户裁定］隐身三层**：不被调用（必须）、不改变既有语义（必须）、完全不可观测（不做且有害）；保留只读内省面。
- **［用户裁定］零新增 syscall**；现有 `SYS_SGEG_*` 整体作废，不改造。
- **［用户裁定］文件名**：`docs/design/sgeg-design.md` 不带版本后缀；版本信息由正文承载；与 `freg-design.md` 一致，避免后续版本无处安放。
- **［讨论共识］四原语**：主体标签、客体标签、转移规则、判定；内核不认识标签名与权限名。
- **［讨论共识］三条减法**：策略语言、身份、可信启动都不进内核；可信启动是前提而非并列组件。
- **［讨论共识］身份路线 A**：判定输入不含 uid；SGEG 只使用身份，不拥有身份；账户与登录移用户态。
- **［讨论共识］兼容红线**：`setuid` 优先、`/proc` 读法不变、`ptrace` 可用、`ld.so` 不被挡、必须有 unconfined 默认域。
- **［讨论共识］强制模型**：标签 + 表；保留 `CAP_*` 并叠加；默认关闭、启用即默认拒绝；加载失败 fail-open + 响亮证据。
- **［讨论共识］跳数模型**：每跳只收窄；授予时验证、使用时验句柄；深度是上限不是惩罚；`fork` 不计深度；分叉是加性、委托是乘性；fork 炸弹归资源层。
- **［讨论共识］触发模型**：被动、无独立调度实体；分类门常驻、判定与状态更新才算激活；跳变是判定结果不是触发条件；判定在建引用时刻，使用端凭 fd；自指由独立主体类型短路。
- **［讨论共识］边界**：恶意用户态程序靠域分离而非收缩权限，走"默认宽、少数关键域收紧"；供应链植入几乎无解，归完整性度量；内核后门归架构隔离；被劫持的合法进程是凭据链主场；总体定位为损害面收敛而非检测。
- **［讨论共识］审计出口**：收在内核侧、单向、只暴露结论，不暴露接口与结构。
- **［讨论共识］失效纪元**：跳数管"传递是否合理"，纪元管"现在是否有效"；使用端只比较一个整数。
- **［讨论共识］跳数定位**：不是触发器，而是判定表字段 `(主体类型, 客体类型, 操作, 跳数档)`，仅在主体标签变更或客体移动时重算。
- **［讨论共识］Rust 设计规则**：返回凭据而非布尔；操作接受对象而非路径；标签类型分离且构造器在 TCB 侧；策略为不可表达非法状态的枚举；跨边界对象统一 `Handle + gen`。
- **［讨论共识］多判据组合**：统一 `decide(subject, object, op, ctx)`，判据全部合取、不得加权打分；跳数与纪元降级为证据项；第一阶段只做跳数、纪元、配额三条 O(1) 判据。
- **［讨论共识］分层短路**：L1 静态表 → L2 动态证据 → L3 有状态判据；L3 只对被标注对象启用，未标注成本为零。
- **［讨论共识］网络边界不做防火墙**：频次、状态、信任边界三条硬性不匹配；只保留稀疏的 `connect` / `bind` / `accept` 判定、socket 客体标签、`SCM_RIGHTS` 传递判定与网络栈域隔离。
- **［讨论共识］socket 作为客体来源**：网络不单独建安全机制，socket 标签直接接入多判据模型，作为 L3 信息流的输入来源。
- **［讨论共识］SGEG 判额度、策略表判权限**：策略表不判"允不允许 fork"，配额判据只回答"已用掉多少"；把既有 `try_charge` / `check_budget` 接进判定路径并赋予可信主体身份。
- **［待定］** OQ-1 客体粒度、OQ-2 拒绝行为、OQ-3 策略所有权、OQ-4 第二阶段时机、OQ-6 存量 syscall 逐条处置、OQ-7 审计出口形态与特权主体、OQ-8 失效纪元粒度与清扫、OQ-9 关键域清单与维护归属、OQ-10 socket 标签粒度与网络栈改造范围、OQ-11 L3 有状态判据启用粒度；另加"委托深度设为 1"的 AI 建议尚未裁定。OQ-5 已闭合为 ［用户裁定］（见上），编号保留。
