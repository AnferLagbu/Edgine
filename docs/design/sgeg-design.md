# SGEG v2 架构设计

> SGEG v2 的目标形态：内核侧收敛为一个**默认关闭、启用即强制**的安全模块，只保留主体标签、客体标签、转移规则、判定四个原语；身份、策略语言、可信启动与审计消费全部退到用户态。新增 syscall 数为 0，既有 `SYS_SGEG_*` 编号整体作废。

## 标注约定

本文所有决策级陈述按来源分三类，行文中逐条标注：

- **［用户裁定］**：用户明确拍板、可直接作为施工前提的结论；
- **［讨论共识］**：讨论中已达成一致并经用户认可，但未以"裁定"形式固定，仍可被新证据推翻；
- **［待定］**：AI 建议、候选方案或尚未闭合的分歧，用户未裁定。全部集中在"开放议题"章，逐条给出待定原因、备选与各自代价。

未标注的内容是**可核查事实**或**基于事实的推导**，不构成决策。本文的周期数与百分比一律是推算量级，不是实测读数。

本文描述的是 SGEG v2 的目标形态；文件名不带版本后缀，版本信息只由正文承载（见 OQ-5）。

事实类引用统一给源码路径与行号；规模数字采用当前代码的可复现实测口径。早前记录中的"约 45 条分发臂、约 96 个类型常量"来自不同统计口径的估算，与当前代码不符，本文不沿用估算值，避免把口径差异写成设计前提。

## 设计动因：一个名字承担了三层职责

### 现状规模与形态

SGEG 当前是一个横跨两个子树的完整子系统：

| 项 | 实测 |
|---|---|
| 代码规模 | `privileged/sgeg` 13 个文件 + `functions/sgeg` 17 个文件（含 `storage/` 2 个），合计 30 个文件、9,302 行 |
| syscall 编号 | 32 个 `SYS_SGEG_*`，其中 31 个占用 **400–415、420–423、453–463 三组非连续编号**（[types.rs:610](src/kernel/privileged/syscall/types.rs) 起），另 1 个 `SYS_SGEG_SCHED_SNAPSHOT` 的编号取自 `edgine_abi::sched` |
| 分发臂 | `functions/syscall/dispatch.rs` 33 条（`SYS_SGEG_DISK_INSTALL` 因 cfg 分两条），覆盖 [dispatch.rs:1375-1530](src/kernel/functions/syscall/dispatch.rs) |
| 类型 / 能力常量 | 分散在多处：`privileged/sgeg/capability.rs` 46 个 `pub const`、`privileged/sgeg/types.rs` 30 个、`functions/sgeg/policy.rs` 26 个 |

编号分布里有一个必须点明的事实：**453–463 这一组已经与 Linux 撞号。** 按 `/usr/include/asm/unistd_64.h`，453 = `map_shadow_stack`、454 = `futex_wake`、455 = `futex_wait`、456 = `futex_requeue`、457 = `statmount`、458 = `listmount`、459 = `lsm_get_self_attr`、460 = `lsm_set_self_attr`、461 = `lsm_list_modules`、462 = `mseal`、463 = `setxattrat`；而 SGEG 在这些号上定义了 `DISK_INSTALL` / `FAT_FORMAT` / `PROC_LIST` / `PROC_SETPRI` / `PROC_SLEEP` / `PROC_CPUTIME` / `GETHOSTNAME` / `SETHOSTNAME` / `BOOT_CHECK` / `REBOOT` / `HOTPLUG_STATUS`。`mseal(462)` 会直接落进 `SYS_SGEG_REBOOT` 的分发臂。335 号（`uretprobe`）在 2024 年被 Linux 占用，说明 400 段被逐步征用不是假设，是趋势。

需要先肯定一点：SGEG 不是完全的空转摆设。seccomp 检查确实位于 syscall 分发硬路径（`privileged/syscall/dispatch.rs` 与 `privileged/proc/seccomp.rs`），文件系统的 `open`、`access`、`mount`、`link` 路径也确实调用能力检查。问题不在"完全没做"，而在"做的位置与承担的职责不匹配"。

### 四个致命缺口

**其一，身份不可持久。** 身份表落盘路径是 `/pwm.db`（[persist.rs:22](src/kernel/functions/sgeg/persist.rs)），`save_database` / `load_database` / `remove_database` 在 [persist.rs:203](src/kernel/functions/sgeg/persist.rs)、[persist.rs:255](src/kernel/functions/sgeg/persist.rs)、[persist.rs:326](src/kernel/functions/sgeg/persist.rs) 定义，随后只被 SGEG 内部的包装层调用（[crypto.rs:304-333](src/kernel/functions/sgeg/crypto.rs)、[identity.rs:114](src/kernel/functions/sgeg/identity.rs)、[identity.rs:480-494](src/kernel/functions/sgeg/identity.rs)），启动编排只调用 `sgeg_init`（[lib.rs:919](src/kernel/lib.rs)），既不加载也不保存。这意味着**创建过的身份在重启后消失**，持久化机制存在但没有接线。

**其二，启动零信任。** `sgeg_init` 用全零公钥初始化（[mod.rs:66-72](src/kernel/privileged/sgeg/mod.rs)），而 `SecureBootSubsystem::init` 只要收到任意公钥就 `enabled.store(true)`（[secure_boot.rs:185-199](src/kernel/privileged/sgeg/secure_boot.rs)）。启动路径没有任何镜像校验，`verify_image`（[secure_boot.rs:228](src/kernel/privileged/sgeg/secure_boot.rs)）只能由 syscall 主动调用。于是 `enabled = true` 的真实含义是"有一个公钥"，不是"启动镜像已验证"。同一份报告也确认：`boot_check_syscall` 只查身份存在性，验签失败不硬阻断（[subsystem-gap-deep-audit.md](docs/report/subsystem-gap-deep-audit.md)）。

**其三，能力检查是库，不是强制点。** 检查散落在 `functions/fs` 的少数入口：`open`、`path`、`mount`、`link` 以及 SGEG 自身接口，例如 [path.rs:91-92](src/kernel/functions/fs/path.rs) 的硬编码 `0x01` 判断与 [mount.rs:52-86](src/kernel/functions/fs/mount.rs) 的挂载检查。`read`、`write`、`unlink`、`socket`、`mmap` 等路径没有等价的检查点。**漏写一处不会让任何审计腿变红**，因为不存在"必须检查"的结构性约束。

**其四，审计链不抗篡改。** 审计哈希用 FNV-1a 64 位串接前序值（[audit.rs:306-320](src/kernel/functions/sgeg/audit.rs)），既无密钥也无签名。任何能写审计区的人都可以重算整条链，链的"连续性"只防误删，不防伪造。

### 其余薄弱面

- **TPM 是软件占位**：8 个 PCR 存在内存数组里（[secure_boot.rs:45](src/kernel/privileged/sgeg/secure_boot.rs)、[secure_boot.rs:347-368](src/kernel/privileged/sgeg/secure_boot.rs)），无硬件根、无密封存储。它可以作为接口形状的预演，不能作为信任根。
- **密码学是混合策略**：SHA-256 自研并带 KAT（[sha256.rs:246-270](src/kernel/privileged/sgeg/sha256.rs)）；常数时间比较自研、以 privileged 为权威（[identity.rs:15-19](src/kernel/privileged/sgeg/identity.rs)）；Ed25519 用 `ed25519-dalek`（[secure_boot.rs:91-100](src/kernel/privileged/sgeg/secure_boot.rs)）；CSPRNG 为 `rdrand` + TSC / 栈地址回退（[csprng.rs:30-58](src/kernel/privileged/sgeg/csprng.rs)）。每一块单独看都有理由，合起来却缺少一份统一的威胁模型——哪些威胁由哪一层承担，没有写清楚。
- **验证面薄**：`kani-harness` 对 SGEG 零引用；host-tests 的权限回归用例以读源码文本、`contains` 断言为主（[fs_permissions_regression_test.rs:167-179](host-tests/tests/fs_permissions_regression_test.rs)、[fs_permissions_regression_test.rs:230-264](host-tests/tests/fs_permissions_regression_test.rs)），是结构锁而非行为验证。
- **存储格式化混入安全子系统**：`SYS_SGEG_DISK_FORMAT` / `SYS_SGEG_DISK_PARTITION` / `SYS_SGEG_FAT_FORMAT` 等臂（[dispatch.rs:1476-1530](src/kernel/functions/syscall/dispatch.rs)）与安全判定无关，属"我需要存储"倒推出来的归属。

### 结构性判断

`Security Guarantee Edgine` 这个名字把**主体身份、访问控制、可信计算**三层职责塞进同一个 syscall 命名空间。后果不是功能少，而是每条能力都停在"想调就调"的层次：调用者必须配合，不配合就没有防线；检查点靠人写，漏写就失效。

由此得到本文的总命题：**把"身份"和"策略"移出内核，把"强制"留在内核。** 内核不认识用户、不认识策略语言，只负责在一次操作上执行一次不可跳过的判定。

## 定位：安全模块，不是安全服务

### 用户裁定

**［用户裁定］** SGEG v2 是**内核安全模块（机制）**，不是安全服务。类比 SELinux：它是内核的一部分，不是"又一个安全 OS 组件"，不提供登录、账户管理、密钥托管之类的服务面。

核心动机来自生态现实：除自写测试程序外，**不会有任何第三方软件调用它，甚至不会知道它存在**。因此它必须"隐身"。

SELinux 的类比对"零新增 syscall"是一条正面证据而非仅仅修辞：SELinux 的控制面是 `selinuxfs` 这个文件系统，不是一组 syscall。策略加载、enforce/permissive 切换、booleans 全部走文件语义。这说明**安全模块完全可以不拥有 syscall 命名空间**，而这正是 SGEG v2 要走的路。

### "隐身"的三层含义

这三层常被混为一谈，必须分开：

| 含义 | 是否做 | 理由 |
|---|---|---|
| **不被调用**（不要求应用配合） | 必须做 | 强制模块存在的意义就是不依赖调用者自觉；靠应用主动上报的机制在生态里等于不存在 |
| **不改变既有语义**（无策略时零差异） | 必须做 | 默认关闭、无策略时行为与无 SGEG 完全一致，是兼容性底线 |
| **完全不可观测** | **不做，且有害** | 故障无法诊断；fail-open 能被接受的前提恰恰是"留下证据" |

正确口径是：**默认不启用、启用后不要求用户态配合、但保留只读内省面**。完全不可观测会把"策略没加载"和"策略加载了但没生效"变成两个无法区分的神秘状态；而一次 fail-open 的启动若没有任何证据，运维只会看到"今天好像不太对"。

### 新增 syscall 数 = 0

**［用户裁定］** SGEG v2 不新增任何 syscall。现有 32 个 `SYS_SGEG_*` 是"为一个不存在的调用者写的接口"，应**整体作废**，不是改造、不是兼容保留。

替代通道全部复用既有语义：

- **策略加载**走"写一个既有路径下的文件"，由用户态策略编译器生成定长表后交给内核；
- **内省**走既有 POSIX 面，例如 `/proc/<pid>/attr/...`、`getxattr`；
- **拒绝留证**写审计记录（落文件或既有日志面）。

这不是暴露 API，是留证。只读内省面与"隐身"不矛盾：正常程序不需要知道它，出问题时运维与审计需要看得到它。

## 形态：内核只保留四个原语

### 四个原语

**［讨论共识］** 内核侧的 SGEG v2 收敛为四个原语，除此之外不做任何策略性工作：

1. **主体标签**：每进程一个，`exec` 时确定，之后不可变（唯一例外是特权重标）。
2. **客体标签**：该对象的安全属性，随客体类型不同而存在不同位置。
3. **转移规则**：`exec` 时由可执行文件的标签决定新标签——M1 用单输入 `可执行文件标签 → 新标签`，**无规则即继承**。双输入形式 `(旧标签, 可执行文件标签) → 新标签` 只在出现"同一二进制在不同上下文需要不同域"（如每用户域）时才需要，届时再扩。
4. **判定**：`(主体标签, 客体标签, 类别, 权限, 纪元) → 允许 / 拒绝`（M1 形态）。"允许但受限"与证据容器在 provenance 引入后启用。

内核**不认识标签名、不认识权限名、不认识策略语法**，只对编译好的定长表做查表。策略语言、策略编译器、类型名与权限名定义全部在用户态。这一条的工程含义是：内核侧没有解析器、没有求值器、没有正则引擎，也没有可能被策略文本触发的递归或内存分配。

### 一次操作的数据流

```
execve:  (旧域标签, 可执行文件标签) --转移规则--> 新域标签
open:    (域标签, 文件标签, 类别, 权限) --判定表--> Allow / Deny -> fd
read:    只验证 fd（fd 已携带授权，不再逐次判定）
```

判定点在"获得句柄"的那一刻，而不是"每次读写"的那一刻。这个位置选择同时决定了性能模型（见"性能"章）：判定是每次打开一次，不是每字节一次。

**使用端不重新判定的边界必须写清**：`read` / `write` 只验 fd 的有效性、该 fd 已携带的授权位与签发纪元（一次整数比较），不再查表。`Witness` 或等价凭据只用于"路径形态"的入口与 crate 内部的转发链，不用于 fd 路径（理由见"判定点的形状"章）。

### 三条刻意的减法

**［讨论共识］** 三条减法都是主动放弃能力，不是尚未实现：

- **策略语言不在内核。** 没有解析、没有求值、没有正则。内核只吃编译结果。
- **身份不进来。** 账户、密码、登录不进内核（见"身份"章）。
- **可信启动不进来。** 它不是 SGEG 的并列组件，而是 SGEG 能成立的前提：**防 root 提权的前提是存在一个比 root 更高的权威，而这个权威只能来自引导链。** 两者是依赖关系，不是并列关系。把可信启动塞进同一个 syscall 命名空间，会让"模块"看起来像一个什么都管的服务，也会让启动期校验与运行期判定互相掩盖失败。

## 判定点的形状：唯一出口，分散存储

这一章回答一个容易被误解的问题：把标签存在文件系统里，会不会让 SGEG 变成文件系统的附属品。

### 外部参照：四家内核的共同形态

| | 判定点 | 客体标签存储 | 结论 |
|---|---|---|---|
| **Windows** | Object Manager 查找时调 SRM 的 `SeAccessCheck`，算法对所有对象类型统一 | 文件的安全描述符由文件系统持久化，内核对象放在对象头 | 检查集中、存储分散 |
| **FreeBSD** | MACF 钩子，`mac_vnode_check_open` / `mac_socket_check_connect` 等 | 每个对象一个 `struct label`（vnode 的 `v_label`、cred 的 `cr_label`），由对象自身的锁保护 | 框架集中、标签分散 |
| **macOS** | 同 FreeBSD（MACF 是 TrustedBSD 的移植） | 沙箱主机制不依赖每对象标签，profile 是每进程的 | 判定集中、标签可缺席 |
| **Linux/SELinux** | LSM 钩子 | `security.selinux` xattr；无 xattr 的文件系统按类型给单一默认上下文 | 同上 |

四家都做到了"判定入口唯一、标签存储按对象类型分散"。**Windows 的文件安全描述符就存在文件系统里，没有人认为 SRM 是 NTFS 的一部分。** 所以"标签存在 inode"不构成附庸；构成附庸的是"判定函数只能被文件系统调用"。

推论：SGEG 的对象模型应当是**一个统一的标签查询接口，加若干按对象类型的实现**。文件系统只是第一个实现者，不是宿主。

### Edgine 的出口现状与两个缺口

好消息是主出口已经存在：`vfs_open_internal`（[handle.rs:59-148](src/kernel/functions/fs/handle.rs)）是唯一的 open 实现，`vfs_open`（[handle.rs:706](src/kernel/functions/fs/handle.rs)）与 `vfs_open_safe`（[handle.rs:586](src/kernel/functions/fs/handle.rs)）都只是转发，且 E6-5 已移除 fallback，**全部文件系统都经 trait object 分发**。在 `fs.fs_open` 成功返回 inode 之后、`OpenFile::new` 与 `OPEN_FILE_TABLE.alloc` 之前插一次判定，可一次覆盖 ext2 / exfat / egfs / ramfs / devfs / overlayfs。

坏消息有两个：

- **`open_by_handle_at_syscall` 绕过它。** 该路径自己解析句柄、自己构造 inode、自己分配 fd（[file_handle.rs:138-190](src/kernel/functions/fs/file_handle.rs)），完全不经过 `vfs_open_internal`。它的权限检查是散装的一次 `pwm_has_capability(pwm, 0, 0x01)`（[file_handle.rs:154](src/kernel/functions/fs/file_handle.rs)）。
- **判定散落在 syscall 入口而不是出口。** 现状正是"每个入口各写一次检查"，于是入口数量等于绕过面数量。

**［讨论共识］** 判定入口必须收敛为一个三段结构：`resolve → authorize → publish`，所有获得对象引用的路径（含 `open_by_handle_at`）都必须走中间那段。这不是 SGEG 的一部分，是 SGEG 能成立的前置工程；没有它，后面写多少判据都是在补漏。

### Witness 的适用边界

**［讨论共识］** "检查返回凭据，让漏检查变成编译错误"只在同一 crate 的纯 Rust 调用链内成立。`vfs_open_internal` 是 `extern "C"` 函数（[handle.rs:59](src/kernel/functions/fs/handle.rs)），跨 C ABI 时 `&Witness` 会退化为裸指针或整数，编译器不再证明"检查过"。

所以类型防线的定位要修正：

- **主路径**靠"结构上唯一出口"保证，靠审计腿数出口数量（而不是数调用点）；
- **`Witness`** 用于 crate 内部的转发链（`link`、`mount`、`rename`、`exec` 内部），那里的调用链是纯 Rust，类型系统才真正有效。

这一修正同时消掉了一处内部矛盾：早期表述一边说 `read` 只验 fd，一边要求 `read` 签名吃 `&Witness`。正确口径是前者——`read` 走 fd，不需要凭据对象。

**第一阶段不实现 `Witness`**（见"落地约束"章的"M1 明确不做的事"）。

## 客体模型：一个查询接口，三个实现

### 客体侧只统一"标签查询"

**［讨论共识］** 客体侧统一的是**一个查询**，不是**一个结构**：trait 只要求对象能回答自己的标签。

- `label`：由各对象自己给出——文件按路径派生，进程读 `label` 字段；
- `epoch`：属于**主体域对象**，不属于客体；
- `gen`：只属于需要稳定身份的对象（进程的 `(pid, gen)`）。**路径派生的文件标签既没有 epoch 也没有 gen**。

早期设计曾把三者塞进一个通用 `SecurityBlob { label, epoch, gen }`，实际会退化成"一半字段永远无意义"：文件侧两个字段都用不上，进程侧又不需要路径。拆开之后，trait 只有一个方法，两个实现各自只持有真正需要的状态。

世代号仍然不是可选的，但它只在需要它的地方出现：inode 会被换出、重建、复用，进程会被回收、pid 会被复用；**只有世代号能保证旧标签不会贴到新对象上**。这不是借鉴 FREG 的哲学，是同一个 bug 的同一个解。

### 薄抽象还是直接内嵌

**［用户裁定］** 选 A（薄抽象）。两种路径的对比如下，A 被采纳的原因是它满足"删掉文件系统后 SGEG 仍然成立"这一检验：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A 薄抽象（采纳）** | 定义"主体标签解析"与"客体标签查询"两个 trait，文件系统、进程各自实现 | 多一层间接（约一个 trait 定义 + 两处 impl）；换来确定性：删掉文件系统，SGEG 的类型、判定、策略表、审计仍在 |
| **B 直接内嵌** | 标签先作为 inode 字段，判定挂在 `vfs_open_internal` | 最快能跑；但 M1 期间 SGEG 事实上是文件系统的一部分，加 socket 客体时要做的不是"加实现"，而是重新分层 |

不做 LSM 式注册表（钩子链表、模块优先级、`security_*` 全树铺开）。理由很直接：FreeBSD 有十多个策略模块才值得铺那套框架，macOS 的 kext 被弃用后框架事实上只剩自家策略；Edgine 只有一个安全模块，注册表是纯粹的过度设计。

### 进程作为一等客体

**［讨论共识］** 进程同时是主体和客体，这两个角色必须分开：

| 角色 | 判什么 |
|---|---|
| 主体 | `exec` 转移、`fork` 继承、降权纪元 |
| 客体 | 谁能对这个进程做什么：`kill` / `tgkill` / `ptrace` / `process_vm_readv` / `process_vm_writev` / `/proc/<pid>/*` / `SCM_RIGHTS` / 共享内存 / `sched_setscheduler` / `setpriority` |

判定是**不对称**的：A 能读 B 的内存，不代表 B 能读 A 的。判定式仍是 `decide(主体标签, 客体标签=进程标签, 动作, 证据)`，不是"同标签互通"。

进程客体比文件客体便宜一个数量级：

| | 文件客体 | 进程客体 |
|---|---|---|
| 持久化 | 需要 xattr 或等价存储 | 不需要，进程结束即消失 |
| 路径语义 | hardlink / rename / bind mount 歧义 | 无 |
| 生命周期 | inode 换出、重建、复用 | 进程生命周期天然管理 |
| 唯一坑 | 标签存储格式 | pid 复用 → `(pid, gen)` |

Edgine 里已经有现成的接线点：

- `process_vm_readv` / `process_vm_writev` 的权限门是 [check_access](src/kernel/functions/proc/process_vm.rs#L86-L99)，当前三档为"自身 / pwm 特权 / uid 相等"，文件头明确写着 `SIMPLIFIED: ... 若后续引入 LSM/能力模型, 应在 check_access 处接入`（[process_vm.rs:23-26](src/kernel/functions/proc/process_vm.rs)）。这是最干净的替换点：把 uid 档换为标签判定，其余不动。
- `get_robust_list` 明确未做跨进程权限检查，注释指出的缺口是"缺统一判定入口"（[clone.rs:564-567](src/kernel/functions/proc/clone.rs)）。
- `kill` / `tgkill` 走 `sys_kill` 的 privileged 四路径分发（[signal.rs:501](src/kernel/functions/proc/signal.rs)、[signal.rs:530](src/kernel/functions/proc/signal.rs)），权限模型需单独确认。
- **`ptrace` 没有 syscall**，`proc/types.rs:185` 只有一个"被跟踪标志"字段。所以"防调试器注入"目前无入口可挂——这不是判定缺失，是功能缺失。

**［用户裁定］** 进程客体进入第一阶段，并排在文件客体之前，作为第一个非文件客体。它不需要文件系统配合，能以最小改动跑通"主体标签 + 客体标签 + 转移规则 + 判定"的完整闭环。

### 线程：归因粒度，不是隔离粒度

**［讨论共识］** 同一进程内的线程共享地址空间、fd 表与凭据，一个线程可以直接写另一个线程的栈与堆。**隔离粒度不可能是线程。**

线程只有两种正当用途：

- **归因**：危险操作记到具体执行流；
- **主体切换**：Windows 的 impersonation token、Linux 的 per-thread `cred`。

因此设计上只允许一件事：**线程可以携带不同的审计主体标签，但不引入"线程之间不能互相访问"的判定。** 后者实现不了，写进文档只会制造一条无法兑现的承诺。

### 文件：两条标签路线

**［用户裁定］** 选 B（路径派生）：标签 = `f(挂载点, 路径前缀)`，在解析时计算，不持久化。两条路线的差别不在实现细节，而在依赖顺序：

| 路线 | 做法 | 依赖 |
|---|---|---|
| **A per-inode** | 标签存 inode，按 `(fs_id, node_id, gen)` 寻址 | 需要文件系统提供**可逆**的 xattr 与崩溃一致性 |
| **B 派生** | 标签 = `f(挂载点, 路径前缀)`，在解析时计算，不持久化 | 只需 mount 时传入该挂载点的标签，不需要改任何文件系统 |

现状阻碍 A：EGFS 的 `setxattr` 只接受 4 个名字槽位，并把值压缩成一个 `u64` 哈希存进 `data_hash`（[egfs_data.rs:1257-1270](src/kernel/functions/fs/egfs/egfs_data.rs)），`getxattr` 返回这个哈希的 8 字节（[egfs_data.rs:1300-1308](src/kernel/functions/fs/egfs/egfs_data.rs)），原始值不可还原；同时磁盘 WAL `zil_persist.rs` 在内核侧零调用者、挂载路径从不重放日志（[subsystem-gap-deep-audit.md](docs/report/subsystem-gap-deep-audit.md)）。

路线 B 不是权宜之计，SELinux 对不支持 xattr 的文件系统就是这么做的：按文件系统类型给单一默认上下文，并用 `mount -o context=` / `fscontext=` 给整盘一个上下文。**代价必须写明**：路径派生标签在 hardlink / rename / bind mount 下会随路径变化，同一 inode 经不同路径可得到不同标签；也无法给同一目录下的单个文件例外。这是**故意接受的语义弱化**，不能表述成"和 SELinux 的 per-inode 等价"。

它的好处是决定性的：**选 B，SGEG 第一阶段就不被文件系统阻塞。**

### socket：暂缓，原因未消

**未核实。** `functions/net/` 的 socket 是否已有独立客体抽象、`privileged/net/` 是否有可挂标签的位置、fd 到 socket 的映射是否已有句柄与世代号，均待查证。若没有，"socket 带标签"不是加字段，是一次结构性改造。粒度与改造范围见 OQ-10。

因此顺序是：**进程 → 文件 → socket**。socket 排在最后不是因为价值低，而是因为它是唯一需要先做客体抽象改造的对象类型。

## 身份：从"拥有身份"到"使用身份"

### 判定输入里不允许出现 uid

**［讨论共识］** 判定输入只允许是域标签，uid 不得作为判定输入。理由很直接：只要 uid 是判定输入，`euid == 0` 就必然在某条路径上短路成放行——这是内核里反复出现的模式，不是实现失误。root 提权于是成为设计的终点，而不是需要防住的目标。

uid 仍然存在，但退化为**普通属性**：用于 `stat` 归属、文件所有权、审计记录、兼容既有程序，不参与"能不能做"的核心判定。主体身份由域标签承担。

### 三条路线

| 路线 | 做法 | 兼容性 | 判断 |
|---|---|---|---|
| **A 标签路线**（SELinux 式） | 内核不管账户，继续用 uid；SGEG 只加标签与判定 | 完全兼容 | **［讨论共识］推荐** |
| B 内核管账户但用 passwd 格式 | 仍需新 syscall 读写账户库 | 破坏"隐身"与"零新增 syscall" | 不推荐 |
| C 独立账户体系（现状 `/pwm.db`） | 内核自带账户库与登录语义 | 与 Linux 二进制兼容性直接冲突 | 淘汰 |

选 A 的推论：**SGEG 不再"拥有"身份，只"使用"身份。** 账户、密码、登录整体搬到用户态——`/etc/passwd` + `/etc/shadow`，由一个 login / PAM 式程序承担。内核只看得到 uid，看不到密码，也不判断"谁是管理员"。

多用户登录这个产品特性不消失，只是不再是内核 syscall。把它做成用户态服务，反而获得了可替换的认证策略（密码、令牌、生物特征）而不触碰 ABI。

### 主体标签从哪来

**［讨论共识］** 三家成熟系统的共同解法是"主体标签由上一环注入"，不是应用自报：

- Windows：登录时 LSASS 创建 token；
- FreeBSD：`login` / `setpmac` / `login.conf` 设置；
- macOS：entitlement 与 launchd、`posix_spawn` 的 spawn attributes 在启动时注入。

对应到 SGEG，主体标签的注入点是 **`exec`**：由父进程或启动器决定，程序自身不参与。`fork` 继承父标签（不递增、不衰减），`exec` 按转移规则重算。**［用户裁定］** 主体标签不复用 `pwm`，另加独立的 `label` 字段（OQ-16 选 B）。`process_get_pwm(pid)` 这类入口说明主体侧已有按进程查询的形状，但 `pwm` 的语义尚未核实，直接复用有把账户语义带回判定输入的风险。

### 必须保留的兼容红线

**［讨论共识］** 以下五条是 rebase（跟随 Linux 语义）的硬边界，逐条都有具体后果，不能当作"以后再补"：

- **`setuid` 语义优先于标签转移。** `su`、`sudo`、带 `s` 位的程序依赖"先换凭据再执行"的既有顺序。若标签转移先于凭据变更生效，要么把提权程序锁在旧域里导致功能失效，要么在转移规则里重新打开一条提权路径。
- **`/proc` 既有字段的读法不能变。** 加字段可以，改顺序、改格式、给既有字段加读限制不行——大量程序按固定格式解析 `/proc`，破坏它等于在不相关的地方制造故障。
- **`ptrace` 在允许时必须可用。** 调试器是开发工作流的一部分；一个"安全"到无法调试的内核会让自身无法维护，也会把开发者推向绕过机制。当前 Edgine 尚未实现 `ptrace`，这条红线的前提是先实现它。
- **`ld.so` 读库路径不能被策略挡住。** 否则程序在 `main` 之前就失败，错误信息极难懂，用户只会看到"程序起不来"。
- **必须有无约束默认域（unconfined）。** 这是 SELinux targeted policy 可用性的来源：绝大多数程序留在默认域，不产生行为差异；只有被明确标记的对象与域进入判定。没有它，默认拒绝会把系统自身先拒绝掉。

## 强制模型

### 既定四条

**［讨论共识］** 以下四条是已经确定的方向：

- **标签 + 表判定**，不做路径字符串匹配，不做运行时求值。
- **保留 Linux `CAP_*` 不动。** 它是 ABI 的一部分，第三方二进制会查询它。SGEG 在 `CAP_*` 之上**叠加**标签判定，而不是替换。两套机制的交集取严：`CAP_*` 不足则拒绝，标签判定不足也拒绝。
- **默认关闭 + 启用后默认拒绝。** "宽容只记日志"（permissive）作为调试档位存在，但不当默认。默认关闭保证不启用时零差异；启用后默认拒绝保证漏配不会静默放行。
- **加载失败走 fail-open + 响亮证据。** fail-closed 会让机器不开机，与"兼容性优先"直接冲突。代价必须诚实写出：**那次启动系统不设防。** 因此失败必须以高可见度留下证据（审计记录 + 内省面可读 + 启动日志），否则 fail-open 就退化成"悄悄没设防"。

### 三种结果，不是两种

**［讨论共识］** 判定结果必须是三值，不能是布尔：

| 结果 | 含义 | 典型场景 |
|---|---|---|
| **允许** | 判据全部通过 | 正常路径 |
| **允许但受限** | 允许本次操作，但主体/客体的能力上限被降低，且写审计 | 来源未知、证据不足、permissive 域 |
| **拒绝** | 任一判据明确否决 | 策略禁止、检测到篡改、纪元失效 |

**M1 的判定实际是二值**：没有"未知来源"的生产者，"允许但受限"退化为域级 permissive 标志。三值在 provenance 引入时启用，此时才第一次出现"证据不足但非恶意"这个输入。

三值的必要性来自误拒控制：**把"不知道"直接映射成"拒绝"，会让信息缺失变成故障。** 正确语义是"最低档不等于拒绝，只等于能力上限降低"——低完整性进程在 Windows 里照样能读文件、能创建进程，只是不能往高完整性对象写。SGEG 取同一口径。

## 传播链：从"跳数"到"格"

这一章记录讨论中修正最多的部分。它纠正了两个直觉：一是"跳数可以当安全度量"，二是"跳数越多越可疑"。**［用户裁定］** 跳数不具主判据地位，它是证据项之一；多判据组合只能单调收窄，不得加权打分。本章是把这条裁定落成可实现形态的推导。

### 范畴纠正：度量问题 vs 证明问题

**OSPF 是度量问题（标量取最小），安全是证明问题（谓词判成立）。** 两者数学形状不同：

- 度量可以相加、可以比较大小；
- 证明只能验证"这条链是否成立"，不能因为"链短"就认为"更可信"。

一条 1 跳但凭据伪造的路径，比 10 跳但每环可验证的路径危险得多。成熟参照都收敛到同一结论：

- **X.509 证书路径验证**：`pathLenConstraint` 的含义是"长度是上限"，不是"越短排名越高"；
- **委托逻辑（Delegation Logic）**：委托是"权限的子集传递"，不是"距离的累加"；
- **seL4 能力派生树**：派生形成树，权限沿树单调收窄；
- **Macaroon / Biscuit**：caveat 链只做衰减（attenuation），不做加权。

共同结论：**深度是约束条件，不是惩罚项。**

### 必须先拆开的五种"跳"

混用这五种"跳"会直接导致错误的策略：

| 跳的类型 | 含义 | 安全相关性 | SGEG 是否需要 |
|---|---|---|---|
| **拓扑跳** | 目录层级、路径深度 | 几乎无关 | 不需要（OSPF 类比只对这类成立，而这类最无意义） |
| **派生跳** | `fork` / `clone` 产生的代际 | 不构成信任边界 | 不需要计入深度 |
| **调用跳** | A 请求 B 代为操作（混淆代理入口） | 高 | 需要 |
| **委托跳** | 真正的凭据链：A 把权限授予 B | 高 | 需要 |
| **数据跳** | 信息流：数据从高密级流向低密级 | 高，但属信息流模型 | 远期，不在第一阶段 |

SGEG 真正需要建模的是**调用跳与委托跳**。把目录深度或 fork 代数算进"跳数"，是在度量一个与安全无关的量。

### 三条严谨核心

**［讨论共识］**

1. **每跳只能收窄，不能扩张。** 衰减（attenuation）/ 权限掩码（rights mask）/ caveat 单调性。seL4 的 rights mask、Macaroon 的 caveat、Biscuit 的链，三套独立演化的系统都收敛到这一条——因为缺了它，任何链式委托都会在某一跳放大权限。
2. **验证在授予时，不在使用时。** 每次 `open` 逐跳验签是 O(深度)，而深度没有上界，热路径会崩。正确做法是：授予时校验整条链，把它坍缩成一个不可伪造的内核句柄；使用时只验句柄。这与 fd 的模型完全相同。
3. **深度是上限加撤销时效，不是扣分项。** 深度用于限制"最多能跨几层"，撤销时效用于限制"旧授权还能活多久"；两者都不是"跳数越多越可疑"的评分。

### 手续链的正确形态：最弱一环

讨论中给出的直觉是"像办理手续，看中途经过了哪些人手，有未知来源或干扰的就扣分"。这个直觉是对的，但**扣分要换成档位**。

一份材料盖了五个章，其中一个是假章——它不会因为另外四个是真章而变成"平均可信"。它就是不可信。这在数学上是**格里的 meet（取下界）**：

```
链的可信度 = min(每一跳的可信档位)
```

而不是 `Σ 权重 / 跳数`。两者差别不是口味：

| | 最弱一环（min） | 加权评分（Σ） |
|---|---|---|
| 加一跳已验证环节 | 不变 | 分数升高，更可信 |
| 加一跳可疑环节 | 直接降到最低 | 只掉一点分，可能仍过线 |
| 是否需要阈值 | 不需要 | 必须有，且阈值无法论证 |
| 可证明性 | 可用偏序关系证明 | 只能证明单个判据 |

"多一道手续不会让材料更可信"这句话本身就在否定加权：加权模型里，多经过一个可信的人办理是会**加分**的。

落地形态：

```
每一跳 → 档位 tier（0 未知 / 1 未验证 / 2 已验证 / 3 引导链背书）
链     → tier_chain = min(所有跳)
判定   → decide(域标签, tier_chain, 客体标签, 动作) → 三值结果
```

链内组合是 meet，判据间组合是合取，两者都不是加法，都满足"只能降、不能升"。

**M1 不实例化 `tier` 字段**：没有 provenance 就没有链，档位恒等于域标签自带的档位，单独存一份是冗余副本。四级定义在此保留，作为 provenance 落地时的语义。

### 缺链的处理：最低档不是拒绝

这是模型能否落地的关键细节。

如果某一跳的 provenance **缺失**，有两种处理：当成"没有这一跳"，则观察到的 min 比真实值高，放行过多；当成"最低档"，则观察到的 min 只可能比真实值低。**第二种才是安全的。**

所以规则是：**不存在"无 provenance"这个状态，只有"provenance 为最低档"这个状态。**

好处是覆盖面不全不再直接变成漏洞，只会变成误拒。这把"链必须 100% 完整"这个不可能的前提，换成了"链不完整就自动更严"这个可实现的性质；再配合上一章的三值语义，最低档落到"允许但受限"，而不是"拒绝"。

### 未知来源与被篡改必须分开

| 情况 | 判定 | 理由 |
|---|---|---|
| 来源未知，无法判断 | 降到最低档（能力上限降低，不必然拒绝） | 信息不足，不等于恶意 |
| 检测到中途被干扰或篡改 | **硬拒绝** | 完整性已破，不是"可信度低"，是对象已被修改 |

把两者都塞进"扣分"，等于让篡改变成"扣一点分"。这是加权模型最典型的危害，也是三值语义必须存在的第二个理由。

### 为什么不用累加：链的完整性是不可能的

不是算法难，是它有一个"全有或全无"的性质：

- 文件标签可以逐目录推进：今天只标注 `/etc`，明天标注 `/home`，中间态仍然可用。
- 传播链不行：只要有一条进程创建路径或一条 IPC 路径不携带 provenance，链就在那里断掉，攻击者从断点重新开始计数。

要让它成立，必须证明"所有可能产生新执行流的路径都携带 provenance"。而 Edgine 目前连前提都不齐：`ptrace` 未实现，`/proc/<pid>/mem` 未核实，`SCM_RIGHTS` 的传递判定尚未确认，共享内存与 futex 没有客体抽象。

对照四家：没有一家用运行时跳数做强制判定。FreeBSD 有十多个策略模块，没有一个用跳数；macOS 沙箱是扁平规则集；SELinux 用静态类型转换图；Windows 用完整性级别标量。这不是没想到，是算过账。

**格是链在无分支情况下的特例。** 一旦允许分支与合并，链就变成格。所以正确选择不是"把链做好"，而是直接选格：同样的单调性拿到全部安全价值，每个主体只需一个档位，不需要全链路完整性证明。

### 跳数剩下的两个位置

**［用户裁定］** 跳数不是触发器，也不具主判据地位。它只剩两个正当位置：

1. **审计字段**：记录"这次操作经过了几次转手、经过谁"。历史属性适合审计，不适合强制——它可以被伪造或丢弃，但作为证据仍然有用。
2. **上限参数**：`max_delegation_depth`，用来截断委托闭包。这是策略参数，不是运行时计数器。

这两处都是"静态配置 + 记录"，不需要每跳维护状态，因此没有完整性难题。

### `fork` 不是委托，跳数不随 `fork` 增长

**［讨论共识］** 子进程继承的是**父标签本身**，不是"父标签 + 1"。同一棵进程树里，每个节点离原点的信任距离相同。若按 fork 递增深度，会精确制造病态：`make -j64` 拉起几百个进程、构建树深 5 层，会被判"跳数超限拒绝"——安全上什么都没防住，正常业务全废。

跳数只计三类事件：**跨信任边界的权限授予、`execve` 上的标签转换、请求代理**。不计 `fork` / `clone`、同域函数调用、目录层级。

一句话概括：**深度衡量横向跨越了多少条信任边界，不是纵向生了几代。**

### 深度与宽度是两件事

**［讨论共识］** 委托是**乘性**的：A → B → C，每一跳都可能放大权限，所以要限深度。分叉是**加性**的：父进程给 1000 个子进程同样的权限，是 1000 份独立、可验证的授权，没有任何一个子进程因此获得父进程没有的权限。

**分叉放大影响面，不放大权限面。** 把两者混进同一个计数器，会既挡不住真正的放大，又误伤正常并发。

### fork 炸弹：不是安全判定，是资源问题

**［讨论共识］** fork 炸弹是 DoS，不是访问控制。"复杂程序"与"炸弹"没有任何静态属性可区分：进程数、树形、标签都一样，唯一区别是速率与生命周期分布——而这两者是运行时统计量，不是策略谓词。

正确归属是资源配额 / 记账，不是策略引擎。SGEG 在这里只有三处正当位置：

1. **谁能 fork / exec**（安全判定）；
2. **子进程继承什么标签**（安全判定）；
3. **资源耗尽时优先牺牲谁**（策略关心资源，但决定"谁死"，不决定"多少算多"）。

记账本身归资源层。接口应当是资源层触顶时**询问**策略"这个域能否使用该额度"，而不是 SGEG 自己去数进程。可以把"某域极短时间内大量 fork"记为**审计异常信号**，但**不触发访问拒绝**。

## 多判据组合

### 统一判定接口

**［讨论共识］** 判定收敛为一个接口：

```
M1:   decide(subject_label, object_label, op, epoch) -> bool
后期: decide(subject_label, object_label, op, evidence) -> Verdict
```

M1 只有纪元一项动态输入，直接做参数。`evidence` 容器与三值 `Verdict` 等 provenance 落地后再启用——提前建容器的代价是调用点要构造一个恒为空的集合，判定函数要遍历一个恒为单元素的集合，收益为零。

### 组合必须合取，且只能降级

**［用户裁定］** 多判据组合取"单调收窄"：所有判据全部通过才允许，任一判据只能把结果往更严的方向推，不能把已拒的改回允许。

三条理由：

- **加权不可证明。** 无法论证"85 分等于安全"——阈值是拍出来的，不是推出来的。
- **可被优化攻击。** 攻击者不必绕过任何判据，只需把总分压在阈值以下：每个判据都"差点拦住"，合起来全部放行。
- **MAC 的数学基础是格，不是分数。** Bell-LaPadula 是偏序关系；引入实数权重会丢掉传递性与单调性。

单调收窄还有一个增量性质：**新判据只会让系统更严，不会让已有保证变松。** 这是安全机制可增量演进的唯一形式。

### 无状态判据与有状态判据

| 判据类型 | 例子 | 现实性 |
|---|---|---|
| **无状态** | 标签比较、档位 meet、纪元整数比较、配额计数 | 现实，O(1)，可穷举验证 |
| **有状态** | 序列、信息流、完整传播链 | 只能局部启用 |

有状态判据的共同难题是覆盖完整性：覆盖 90% 等于覆盖 0%，因为缺口就是绕过面。这不是算法复杂度问题，是"全有或全无"的问题。所以它们只能用"标注"开关限制在少数域上，不能全局启用。

### 四个候选判据

| 判据 | 防什么 | 成本 |
|---|---|---|
| **档位（原跳数）** | 委托提权的传递闭包 | 一次 min 比较 |
| **纪元** | 旧授权继续有效 | 一次整数比较 |
| **配额** | 累积型行为：fork 炸弹、写满 inode、挤占页缓存 | 一次计数器比较 |
| **序列 / 信息流** | 单步合法、组合成攻击；合法读取后的外泄 | 需存状态，只对被标注对象启用 |

### 三类明确不归 SGEG

- **时序与侧信道**：归调度与架构（缓存分区、常量时间、抢占策略）。
- **完整性度量**：归 `secure_boot` 那条线（见"边界"章的供应链植入）。
- **真正意义上的入侵检测**：归审计与行为基线。

理由一致：把这些塞进判定器只会拉长判定路径，让"简单"失守。

### 分层短路

判据按"成本 × 失败概率"排序，任一层拒绝即返回：

| 层 | 内容 | 成本 | 覆盖面 |
|---|---|---|---|
| **L1 静态表** | 定长表查表，含域与客体标签 | O(1) | 绝大多数操作死在这一层 |
| **L2 动态证据** | 档位、纪元、配额，均为字段比较 | O(1) | 累积型与时效型行为 |
| **L3 有状态判据** | 序列、信息流 | 需存状态 | 只对被标注的主体或客体启用；未标注不进该层，成本为零 |

分层的意义不是"更快"，而是**让最贵的判据只作用在最小的集合上**。

### 第一阶段只做 L1 加纪元

**［用户裁定］** 第一阶段的内容是：**静态表 + 纪元 + 进程客体判定 + 文件客体判定（路径派生）**。

这里要诚实标注两处收缩：

- **档位在第一阶段退化为字段**：委托深度尚未启用，`tier` 恒取域标签的档位，链长为 1；
- **配额不在第一阶段**：它依赖 `cgroup.rs` 的 `try_charge` / `check_budget` 接线（当前全仓无调用者，见"落地约束"），SGEG 单方面无法把它接进判定路径。

把"档位、纪元、配额三条"写成第一阶段会让里程碑看起来比实际饱满。真实的第一阶段只能防住"被标注客体被未标注域直接访问"，以及"纪元失效后继续使用旧授权"。把这句话写明，比多列两条判据更有价值——因为它是唯一可以被穷举验证的部分。

## 误拒控制

误拒是这套机制能否被使用的分水岭。先纠正一个方向性问题：**增加判据通常让误拒变多，不是变少。** 合取意味着任一拒绝即拒绝，每加一条判据就多一个拒绝理由。误拒的主因不是判据不够准，而是下面两件事。

### 两个根因

| 根因 | 表现 | 有效手段 |
|---|---|---|
| **策略缺失**（主因） | 该放行的规则没写，默认拒绝命中它 | 不判定、只记不拒、可读反馈 |
| **把"不知道"当成"不允许"** | 来源未知直接拒 | 最低档 → 能力上限降低，不必然拒绝 |

### 五层规避，按有效性排序

1. **根本不判定。** unconfined 默认域。这是 SELinux targeted policy 可用性的来源，也是误拒率最低的手段——不是判得更准，是让判定不发生。
2. **判了但只记不拒。** 逐域的 permissive 档。关键是**逐域而不是全局**：全局 permissive 等于整套机制失效。
3. **未知降级而非拒绝。** 三值语义：允许 / 允许但受限 / 拒绝。
4. **拒绝要可读、可反馈。** 审计记录直接给出 `(主体标签, 客体标签, 动作, 缺哪项判据)` 四元组，让补规则变成机械操作。SELinux 的 `setroubleshoot` 就是把 AVC 拒绝翻译成"缺哪条规则"，没有这个，运维只能看到"程序起不来"。
5. **粗粒度起步。** 路径派生标签的误拒率显著低于 per-file 标签，因为它不会因为漏标某个文件而拒。先粗后细，是降低误拒最省力的旋钮。

### 豁免只有一种形态

**［用户裁定］** SELinux 的豁免机制有多种形态，适合 Edgine 的只有两种，而且要加一条硬约束（与 OQ-3 选 C 一致）：

| 机制 | 是否采用 | 理由 |
|---|---|---|
| `dontaudit` | 不采用 | 让真实问题隐身，与 fail-open 必须"留证据"冲突 |
| 布尔开关（booleans） | 不采用 | 需要运行时写接口，与零新增 syscall 冲突 |
| permissive 域 | **采用** | 调试档的正解，逐域生效 |
| 策略规则本身写"允许" | **采用** | 最直接，但要求策略作者知道该写什么 |

硬约束：**豁免只能通过"改策略文件 + 重启"生效，不接受运行时开关。**

理由：豁免的本质是"关掉防护"。如果运行时能关，攻破 root 之后第一步就是关掉它，SGEG 对 root 提权完全失效——这与 OQ-3（策略所有权）是同一个问题。把豁免绑到"改文件 + 重启"，等于把它的权威绑到引导链，而不是绑到某个进程的权限上。代价是运维不便，换来的是口径一致。

### 上线必须是两个档位

SELinux 的标准流程应当内建为设计能力，而不是运维技巧：

1. 新策略先以 permissive 运行，收集"本会被拒"的清单；
2. 人看清单，区分"策略漏写"与"确实该拒"；
3. 补规则，切 enforcing。

没有第一步，enforcing 上线必然大规模误拒。这也是"默认关闭"之所以必要的原因：第一次启用必须是观察模式。

### 一个必须承认的取舍

"减少误拒"与"提高覆盖"是同一个旋钮的两端。能做到的最好状态是：**误拒集中在少数被明确标注的域里，而这些域的误拒由人主动承担。** 这正是"默认宽、少数关键域收紧"的含义——不是让判定更聪明，是让判定的发生范围足够小，小到每一条规则都有人负责。

## 授权时效：失效纪元

**［讨论共识］** 档位与凭据链只能回答"这次授权传递是否合理"，回答不了"这份授权现在是否还应该有效"。一个攻击者可以走在一条每个维度都完美的路径上：凭据完整、每跳收窄、档位很高，但它持有的授权可能早已该撤销。

失效纪元（revocation epoch）作为第二判据：

- 主体标签降级时（例如从高信任域降到低信任域），递增该主体的纪元号；
- 已发出的凭据携带**签发时的纪元**；
- 使用时刻比较一对值：凭据的 `(域标识, 纪元)` 等于当前域的 `(域标识, 纪元)` 才有效，否则凭据失效。**只比整数会误判**——两个不同域可能有相同的纪元值，必须与域标识配对。

代价与收益必须一起写：

- **代价**：一次降权需要扫一遍在途凭据（或按纪元批量作废），这是一次冷路径的全局动作；
- **收益**：稠密路径仍然只有一次整数比较，既优于"每次 `read` 重新判定"，也优于"授权一次、永久有效"这两个极端。

它与档位互补：档位管"横向跨了几条信任边界"，纪元管"纵向过期了没有"。具体粒度与在途凭据的清扫方式见 OQ-8。

## 触发模型与激活时机

**［讨论共识］** SGEG 是**被动的**：它不拥有任何自己的线程、定时器或轮询，只挂在受保护操作的入口上，跑在调用者的上下文与配额里。这是"隐身"的技术基础——没有独立调度实体，就没有可观测的进程、设备节点或 procfs 入口可供发现；它的运行成本也天然计入调用者。

### 钩子内部的三段

一次钩子调用分三段，**只有中间一段算"激活"**：

| 段 | 动作 | 成本量级 |
|---|---|---|
| 分类门 | `(主体类型, 客体类型)` 二维表查一个"有无策略"位 | 纳秒级，常驻 |
| 判定 | 查定长表、比较档位与纪元 | 激活后才发生 |
| 状态更新 | `exec` 换域、`fork` 继承、`open` 后 fd 带走授权 | 激活后才发生 |

关键区分：**跳变是判定的结果，不是触发条件。** 先有"这次操作要不要判"的分类，才有判定；判定产生标签变化，变化再写回状态。

### 为什么不能以"跳变"为触发器

- **累积型攻击不产生跳变。** fork 大量子进程、写满 inode、挤占页缓存，这些行为里标签不变、档位不变、域不变。若只在跳变时判定，这类攻击的拦截次数是零。
- **识别跳变本身要常驻执行。** 要发现"跳变"，必须在每个操作上比较前后状态；既然常驻比较不可避免，就不如把它做成一次显式的分类门查表。

### 稀疏性的真正来源

判定并不稀疏，**授权稀疏、使用稠密**：

- 判定发生在**建立引用的时刻**：`open`、`exec`、`mount`、`bind`、`link`、`rename`、`ptrace`、`kill`、`socket`；
- 使用时刻（`read` / `write` 循环、缺页、`mmap` 命中）手里拿的是已带授权的 fd，**fd 即凭据**，不再查表。

这同时是 TOCTOU 的正解：检查与使用之间不存在"再解析一次路径"的窗口，因为使用端拿到的是对象引用或句柄，不是路径字符串。

### 三个必须主动的时刻（都在钩子路径之外）

- **boot / mount**：装载客体标签与策略表；
- **策略更新后**：全量重验证，而不是等下一次访问逐条发现失效；
- **exec**：重算主体标签与转移结果。

这三件事不能挂在"某次文件访问"上，因为它们要么发生在任何用户操作之前，要么需要全局视野。

### 自指短路

**SGEG 不得判定自身**，否则一次判定会触发另一次判定，递归没有终点。处理方式是：内核主体域整体豁免，并且**豁免由独立的主体类型在类型层面保证**，不能用一个布尔开关——布尔开关会被误翻，独立类型不会。这与"策略为不可表达非法状态的枚举"是同一条设计规则。

## 性能

> 本章所有数字均为**推算量级，非实测**。它们的用途是判断架构方向是否成立，不是验收指标。

### 第一阶段：标签判定

| 动作 | 推算成本 | 说明 |
|---|---|---|
| 读进程标签 | 1–2 周期 | `exec` 后不可变、无锁、通常 L1 命中 |
| 读客体标签 | 1–3 周期（热）/ I/O（冷） | 存在 inode 或按路径派生；派生路径无 I/O |
| 查表 | 20–40 周期 | AVC 式 `(主体 × 客体 × 类别)` 缓存，命中率极高 |
| 合计 | 约 10–20 ns | 单次打开 |

相对开销的推算：

- 策略未加载：约 0（一条原子读短路）；
- 真实负载：1–3%；
- `open` 密集型微基准（`find`、包管理器、通配匹配）：5–10%。

原因不是"实现得快"，而是判定位置选对了：**判定是"每次打开一次"，不是"每字节一次"。**

### 两个隐性成本

- **结构体膨胀。** 给进程或文件描述符加标签字段，可能把恰好占满 cache line 的结构挤过边界，带来的代价可能大于查表本身。设计时应把标签打包进既有 padding，而不是新增字段。
- **冷路径。** per-inode 标签在挂载后首次访问、或 inode 缓存淘汰后重读是真实 I/O，对"扫全盘"类操作是"访问次数 × I/O"的放大。**路径派生标签没有这一项**，这是它相对 per-inode 的一个额外收益。

### 第二阶段：凭据与档位

带 provenance 的 IPC 每消息需要 join 一次档位，合计约十几 ns / 次；对 pipe / 微服务密集负载约 5–15%。

**真正的代价不在周期，而在改动面**：所有 IPC 机制（socket、pipe、信号、共享内存、futex）都要携带 provenance 并参与判定，每漏一处就是一条绕过路径。浮动标签必须作用域化到一次操作——否则守护进程处理过一次不可信请求后就被永久污染。

### 三个便宜的优化

**［讨论共识］**

- **检查点下沉到建引用处。** fd 天然是授权凭证，大文件 I/O 的开销归零；这与"检查返回凭据而非布尔"的 Rust 设计规则同源。
- **策略重载无锁换代。** 换指针 + 宽限期回收旧表，读路径永不加锁。与 TLB 代（generation）同思路。
- **策略未加载用单条原子读短路。** 默认关闭时热路径只多一条原子读，不进入判定函数。

### "类型数 ≤ 256"是性能设计决策

这不是命名洁癖，而是架构约束：类型数若无上界，`(主体 × 客体 × 类别)` 的二维表会爆掉，只能退回"哈希 + 缓存"，命中率与最坏延迟都不可控。把类型数压在 256 以内，表就可以是定长、可预计算、可放进 L1/L2 的结构。**上界换来确定性。**

### 计量从第一天做进去

必须从一开始就采集：判定次数、缓存命中率、拒绝次数、平均周期。理由是：

- 几乎零成本（几个每 CPU 计数器）；
- 它是唯一能回答"到底贵不贵"的依据，而不是靠估算；
- 它同时是用户态策略编译器的输入——编译器需要知道哪些规则被频繁命中，才能优化表的布局。

## Rust 特性：真实优势与蒸发处

### 生命周期带来的三条真实优势

1. **作用域化的临时标签。** 浮动标签在 Rust 里是持有 `&mut` 的 guard，出作用域必然恢复，早返回也恢复。C 里是 save / restore 配对，真实 bug 几乎全是某条 `goto out` 漏了 restore。
2. **"检查后使用"不可拆开（TOCTOU）。** C 的经典提权原语是 `access()` 之后 `open()`：两次解析路径，中间可被替换。若检查返回的是**到对象的引用**而非布尔，就不存在"再解析一次"，检查与使用被类型系统焊在一起。
3. **能力靠所有权表达。** `File` 拥有权限，`&File` 即能力，没有 `&File` 写不出 `read`。这就是 Capsicum 模型，但不需要新 API，因为它是 Rust 的默认形状。

### 类型系统带来的优势

- **newtype 严格区分** `SubjectLabel` / `ObjectLabel` / `TrustLevel`，防止把主体标签当客体标签传；
- **sealed / 私有字段**使标签不可伪造，构造器只在 TCB 侧；
- **策略解析成枚举**后"非法状态不可表达"，校验一次在加载，热路径无条件信任形状；
- **`#[must_use]`** 让忽略拒绝成为告警；
- **`#![forbid(unsafe_code)]`** 使策略引擎自身不可能被内存破坏。

### 类型防线在 Edgine 里的适用范围

早期表述把"检查器返回 `Witness`、未通过检查的调用编译不过"列为最大优势。这个判断需要按 Edgine 的实际形状收窄：

- **主路径拿不到这个保证。** `vfs_open_internal` 是 `extern "C"`，跨 C ABI 时 `&Witness` 退化为裸指针或整数，编译器不再证明"检查过"。
- **crate 内部转发链拿得到。** `link`、`mount`、`rename`、`exec` 的内部调用是纯 Rust，类型系统有效。

所以正确分工是：主路径靠"结构上唯一出口"（见"判定点的形状"章），内部链路靠 `Witness`。这不是削弱 Rust 的价值，是避免把一条保证写到它不成立的位置上。当前靠审计脚本盯"编号已声明但未接线"确实是用工具补语言的短板；把"必须检查"抬到类型层仍然值得做，只是射程要标清。

### 优势蒸发处

必须写清楚，否则会高估 Rust 的作用：

- **`panic = "abort"` 下 Drop 不执行。** guard 只在正常路径成立，panic 路径上恢复动作不发生，需要第二道保险，不能把 RAII 当作唯一保证。
- **内核里很少拿得到 `&mut`。** 共享状态通常在 `IrqSpinLock` 后面，借用检查器**看不懂锁保证了互斥**，编译期不再证明"同一时刻只有一个修改者"。锁纪律仍然要靠审计与约定。
- **保证在 TCB 边界终止。** `privileged/` 的 `unsafe` 会把引用擦成裸指针或 `&'static`；buffer 被释放重建后，安全层仍持旧引用即 UAF。这正是 FREG 的核心问题，**Rust 救不了经 `unsafe` 逃逸的引用**，所以必须 `Handle + gen`。SGEG 同理：客体标签挂在 inode 或进程上，对象被换出、重建、复用后旧句柄必须被拒。
- **用户输入永远是未验证整数。** 生命周期对"这个 `u64` 是不是有效 fd"毫无帮助，边界校验仍要显式做。

一句话：**Rust 消掉了编译器可见的那部分 UAF，消不掉穿过 `unsafe` 的那部分。**

### 四条设计规则

**［讨论共识］** 优势不是"用了 Rust 就有"，是按 Rust 形状设计 API 才有：

1. **检查返回凭据，而不是布尔。**
2. **操作接受"拥有权限的对象"，而不是路径。**
3. **标签类型严格分离，构造器只在 TCB 侧。**
4. **策略加载后是"不可表达非法状态"的枚举。**

并主动放弃一条幻想：**不要指望生命周期替管跨边界对象的寿命。** 凡可能被重建的对象统一用代号句柄。

## 落地约束

### 出口收敛是前置工程

`open_by_handle_at_syscall` 绕过 `vfs_open_internal` 的事实（见"判定点的形状"章）意味着：**在收敛出口之前，SGEG 的任何判定都只覆盖部分路径。** 这一项必须先做，且它的验收标准是可机械检查的——**统计能获得对象引用的出口数量，要求其为 1（或全部经过同一个 authorize 函数）**，而不是逐个人工确认调用点。

### 文件系统依赖只在 per-inode 路线上存在

早期结论"SGEG 的落地被文件系统卡在后面"成立于 per-inode 标签路线。第一阶段已定选路径派生（［用户裁定］，OQ-13 选 B），于是：

- 不需要 EGFS 提供可逆 xattr；
- 不需要等崩溃一致性闭环；
- 需要文件系统配合的只剩"mount 时把该挂载点的标签传进 VFS"——这是 mount 路径的事，不是 EGFS 的事。

因此"被文件系统卡住"应改述为"**per-file 粒度被文件系统卡住**"。第一阶段有不依赖文件系统的可行入口。

### 资源记账：机制在，接线断

记账原语并非完全不存在：`privileged/proc/cgroup.rs` 已有 `try_charge` / `check_budget`，也有 `cgroupfs` 面。但全仓没有调用者把它们接到 fork、内存分配或调度路径上——与 `/pwm.db` 是同一类问题：机制在、接线断。

因此 fork 炸弹类问题**现在不是"SGEG 判错"，是"没有地方判"**。缺的是 OOM 分级、按域的优先牺牲裁决，以及"资源层触顶时询问策略"的接口。这属需单独立项的缺口，不应塞进 SGEG 的判定表里凑数。

### 进程侧的既有缺口

- `get_robust_list` 未做跨进程权限检查（[clone.rs:564-567](src/kernel/functions/proc/clone.rs)）；
- `ptrace` 未实现，只有"被跟踪标志"字段（`proc/types.rs:185`）；
- `/proc/<pid>/mem` 是否存在、`SCM_RIGHTS` 是否已有传递判定，均未核实。

**进程侧防护的覆盖面，取决于被保护的操作是否已经实现。** 没实现的 syscall 谈不上防护，这一条要在排期时先盘清。

### M1 明确不做的事

这一节把"定义了但第一阶段没有使用者"的项钉住，避免后续讨论反复捡回。

| 项 | 状态 | 原因 |
|---|---|---|
| `Witness` 类型 | 不做 | 主路径是 `extern "C"`，用不上；内部链在 M1 只有一条路径，直接调判定即可 |
| `max_delegation_depth` 与审计跳数字段 | 不做 | provenance 推到 M2，没有链就没有输入 |
| L2 / L3 分层的代码结构 | 不做 | M1 只有"查表 + 比较纪元"，一个函数即可；分层是描述，不是骨架 |
| `tier` 字段 | 不实例化 | 恒等于域标签自带档位，存一份是冗余副本 |
| 三值 `Verdict` 与 `evidence` 容器 | 不做 | 没有"未知来源"的生产者；M1 用二值 + 域级 permissive |
| 通用 `SecurityBlob` | 不做 | 文件侧无 `epoch` / `gen`，统一结构会退化成一半字段空置；只保留"标签查询"trait |
| 转移规则双输入 | 不做 | M1 单输入足够；双输入只在每用户域这类场景需要 |
| `get_robust_list` / `/proc/<pid>/mem` / `SCM_RIGHTS` / 共享内存判定 | 不做 | 前两者缺统一判定入口，后两者功能本身未实现 |
| 挂载代次字段 | 不实例化 | M1 没有运行期重挂载，字段没有变化源 |
| 高敏标签禁止 `mmap` | 不做 | 收益窄、误分类的诊断成本高；列为可选收敛手段 |

判定标准统一为一句话：**没有真实输入源的字段与分支，一律不写。**

## 边界：SGEG 不解决的攻击类型

把"内部攻击"当成一个整体，是设计上最常见的偷懒。它至少分四类，SGEG 对每一类的答案不同。

### 恶意用户态程序 ［讨论共识］

**有解，但解不是"收缩权限"，而是"域分离"。**

- 限制 syscall 只在程序无法提权时有用：一旦它拿到 root，限制清单本身就可以被它改写或绕过，防线归零。
- 把它关进一个只能访问自身数据的域，损失才有界。
- 代价是**必须为关键域预置策略**。而 Edgine 没有发行版、没有打包体系、没有维护 refpolicy 的人力，因此只能走"**默认宽、少数关键域收紧**"，不能走"默认严 + 白名单"。

### 供应链植入 ［讨论共识］

**几乎无解。** 对 SGEG 来说，被植入的程序执行的是合法的 `exec`、携带完整的凭据、档位也合理——它在判定表的每一个维度上都"正确"。这类攻击只能靠完整性度量（签名、度量日志、远程证明）与系统外防线（构建可复现、制品签名、发布审计）。

现状必须写明：`secure_boot.rs` 的 `verify_image` 只有一个 `EG_SECURE_BOOT` syscall 入口（[types.rs:850](src/kernel/privileged/syscall/types.rs)、[dispatch.rs:293-296](src/kernel/privileged/syscall/dispatch.rs)），且平台密钥全零初始化（[mod.rs:66-72](src/kernel/privileged/sgeg/mod.rs)）。这一层目前是空壳，属**独立缺口**，不是 SGEG 的职责。

### 内核内后门 ［讨论共识］

**答案在架构，不在运行时策略。** Framekernel 的 `privileged/` 与 `functions/` 分界、`#![deny(unsafe_code)]`、依赖单向、审计脚本，共同把"可作恶代码"收缩到一小块可审查的 TCB。结构性隔离强于运行时判定：一段已经在 ring 0 里、且能改页表的代码，任何策略表都拦不住它。

因此 SGEG 不应试图覆盖这一类。声称"安全模块能防内核后门"的机制，通常只是把后门挪到了策略引擎里。

### 被劫持的合法进程 ［讨论共识］

**这是 SGEG 的主场，也是相对 SELinux 的唯一差异化。** SELinux 的类型转换是静态的：它知道"哪个域在发请求"，但不知道"这个请求代表谁发出"。

这里有两层，之前的文档只写了第一层：

- **代理层**：一个被攻破的浏览器让 root 守护进程代为打开文件时，守护进程的域是合法的、凭据是完整的。这靠传播链解决，属第二阶段。
- **直接层**：被攻破的进程直接读别人的内存、注入调试器、杀进程、偷 fd。这靠**进程作为客体**解决，不需要任何传播链，属第一阶段。

**直接层是更划算的投入**：它不需要 provenance 的完整性，判定点是现成的 `process_vm` / `kill` / `/proc` 读取，而且在 Edgine 里已有 `check_access` 这样的接线点。

### 撤销的时间窗口 ［用户裁定］

判定在建立引用时刻完成，纪元只负责撤销已发出的引用。两者的生效时机不同：

- **新引用**：纪元递增后，新的 `open` / `connect` 立即按新纪元判定；
- **已发出的 fd**：每次 `read` / `write` 比较一次整数，降级后下一次操作即失败；
- **已建立的映射**：缺页时比较 VMA 携带的纪元。

**残余窗口**：已驻留页不受影响。降级时已经 fault 进来的页仍然可读，可写映射同理（脏页还可能已回写）。要彻底闭合只能主动 `unmap` / `mprotect` 并做 TLB shootdown，属重操作。

对照：SELinux、FreeBSD MAC、Windows、macOS 沙箱都只在建映射时判定一次，**连新缺页都不检查**，已有映射在策略变化后继续可用；只有 seL4 能真正撤销映射，代价是显式删除能力并遍历页表。

本设计比上述四家严格一档，剩余缺口用两条低成本手段收敛：**`fork` 不继承纪元过期的 VMA**；高敏对象禁止 `mmap` 作为可选策略手段（不进第一阶段）。主动 unmap 在当前裁定下不实现——策略固定于启动期、不做检测，缺少运行期降级触发源；若将来允许运行期策略更新或引入可信降级触发源，此项需重新评估。

### 定位：损害面收敛，不是检测

**［讨论共识］** SGEG 对内部攻击的作用是**损害面收敛（containment）**，不是**检测（detection）**。

病毒与后门的共性是**以合法身份运行**。MAC 的哲学是不看意图、只看能力：它能防越界，防不了界内破坏。检测需要完整性度量、行为基线、异常检测等另一套机制，与判定表不是同一个东西。

因此必须有一节明确写出"SGEG 不解决什么"——否则每一次没防住都会被读成"模块有 bug"，而不是"这不在它的能力范围"。

### 隐身与可观测性的张力 ［讨论共识］

用户态看不到 SGEG，意味着用户态也无法通过它做审计告警。解法不是把接口暴露出去，而是：

- **审计出口收在内核侧**，单向写入；
- 通道只有特权主体可读，普通程序既看不到接口，也看不到结构；
- 只暴露**结论**（谁在何时被拒、命中哪条规则、是否 fail-open），不暴露策略表与标签布局。

通道形态与"特权主体"的界定见 OQ-7。

### 网络边界：为什么不做防火墙 ［讨论共识］

两个问题本质不同：防火墙回答"**这个包该不该进出**"，SGEG 回答"**这个进程该不该开这个口子**"。

**三条硬性不匹配。**

- **频次。** MAC 是稀疏的：建引用时刻判定一次；包过滤是稠密的：每包一次。合并会把判定路径推进软中断与 NAPI 上下文，而 SGEG 的前提是跑在调用者上下文、可阻塞、可审计、失败可返回错误码。
- **状态。** SGEG 的判定是无状态纯函数，这是它能被缓存、被穷举测试、被形式化论证的根本；防火墙需要连接跟踪状态机，一旦引入流状态，纯函数性质作废。
- **信任边界。** 包过滤的输入是不可信数据，需要在内核解析协议头、处理分片重叠与 IP 选项，这是内核漏洞最集中的区域。SGEG 的输入必须是内核已经结构化好的事实，不能是原始字节。

**SGEG 在网络边界的四个正确位置**（都稀疏、都落在建引用时刻）：`connect` / `bind` / `accept` 的命名判定、socket 作为客体带标签、`SCM_RIGHTS` 传递判定、网络栈本身作为一个域。

**未核实项。** Edgine 网络栈当前的实现程度、socket 层是否已有独立的客体抽象，均待查证。若没有，"socket 带标签"不是加字段，而是一次结构性改造，见 OQ-10。

## 开放议题

以下保留全部 OQ 编号：未闭合项标 **［待定］**，已闭合项标 **［用户裁定］**；编号不重排，便于与既有讨论对照。

### OQ-1 客体标签粒度 ［用户裁定 · 选 A］

**问题。** 粒度决定安全覆盖面，也决定与 Linux 语义冲突的面积。粒度越细，判定点越多，绕过路径也越多。

**备选与代价。**

| 备选 | 覆盖 | 代价 |
|---|---|---|
| A 仅文件 / 目录（per-inode） | 持久对象 | 与 xattr 同构；IPC 面完全无覆盖；**被 EGFS 的 xattr 缺陷阻塞** |
| B A + socket / 共享内存 / 进程间通道 | 持久对象 + IPC | 需要内存侧表与 `Handle + gen`；判定点扩展到全部 IPC |
| C 全部内核对象 | 最大 | 需要完整对象模型，与 fd 对象模型设计强耦合 |
| **D 按挂载点 / 路径前缀派生，不持久化**（AI 建议） | 持久对象，粗粒度 | 不依赖文件系统改造；hardlink / rename / bind mount 下标签随路径变化，无语义等价性 |

**裁定。** 采用 A：第一阶段只覆盖文件与进程，不给 pipe / socket 打标签；文件粒度按 OQ-13 的路径派生落地。`SCM_RIGHTS` 当前未实现（[syscall.rs:607](src/kernel/functions/net/syscall.rs) 标注 deferred），因此"经 fd 传递把标签带过边界"这条主要绕过路径暂不存在，先做 A 不留下明显缺口。B 推到 M2。

### OQ-2 拒绝时的行为 ［用户裁定 · 选 D］

**裁定。** 采用 D：`EACCES` + 审计 + 速率限制。只返兼容错误码而不终止进程，避免误报杀掉构建工具与守护进程；同时用审计与限流把探测成本显性化。限流依赖资源记账接线，在记账接通前只有前两项生效。

**备选与代价。**

| 备选 | 行为 | 代价 |
|---|---|---|
| A 仅 `EACCES` | 兼容 | 允许探测与回退 |
| B 拒绝即终止进程 | 强 | 误报代价高 |
| C 按域配置 | 灵活 | 引入策略表达力与所有权问题 |
| D `EACCES` + 审计 + 速率限制（AI 倾向） | 折中 | 不阻断探测但留下证据；限流需资源记账支持 |

三值语义（允许 / 允许但受限 / 拒绝）落地后，本条的实际问题是"受限态用什么错误码暴露"，需要单独定。

### OQ-3 策略的所有权 ［用户裁定 · 选 C］

**裁定。** 采用 C：策略在启动期固定，改策略需重启，权威绑到引导链而不是绑到某个进程的权限。这与"豁免只能改文件 + 重启"同源：若运行期可改策略，攻破 root 后第一步就是关掉防护。运维不便的代价被明确接受。

**备选与代价。**

| 备选 | 谁能改 | 代价 |
|---|---|---|
| A 任意 root | 简单 | 对 root 提权无效 |
| B 仅签名策略 | 持签名密钥者 | 需要密钥管理与离线签名 |
| C 启动期固定，改策略需重启 | 引导链 | 最强，运维成本高 |
| D 启动期基线 + 运行时签名的增量 | 分层 | 表达力与安全性兼顾，最复杂 |

C 已采纳：启动期固定、改策略需重启。运行期更新策略不在第一阶段考虑。

### OQ-4 第二阶段（provenance / 信任链）是否做、何时做 ［用户裁定 · 选 B］

**裁定。** 采用 B：第一阶段稳定后再做 provenance。防混淆代理的需求成立，但全部 IPC 机制都要携带 provenance，在对象模型未收敛前做等于返工。

**备选与代价。**

| 备选 | 时机 | 代价 |
|---|---|---|
| A 不做 | 永不 | 接受混淆代理风险 |
| B 第一阶段稳定后做（AI 倾向） | 中期 | 依赖顺序清晰；期间存在已知缺口 |
| C 与第一阶段同批做 | 立即 | 改动面最大，对象模型未定前无法收敛 |

按"格替代链"的口径，第二阶段要做的是"档位 + 派生单调"，不是"链长累加"，见 OQ-15。

### OQ-5 文件名是否带版本后缀 ［用户裁定 · 已闭合］

**［用户裁定］** 文件名不带版本后缀，定为 `docs/design/sgeg-design.md`；版本信息只由正文承载，不进文件名。

理由：与 `freg-design.md` 的命名一致；文件名带版本会让后续版本无处安放——同一份设计应随演进直接改正文本体，而不是并列堆放快照。

### OQ-6 现有 32 条 syscall 的逐条处置 ［用户裁定 · 选 A］

**裁定。** 采用 A：一次性全部删除。删除范围包括用户态库（`src/user/lib/src/sys.rs` 仍有 18 处 `SYS_SGEG_*` 引用）、测试与文档；453–463 已与 Linux 撞号，继续保留会持续遮蔽 Linux 系统调用。

**新增约束：453–463 已与 Linux 撞号**（`map_shadow_stack` … `setxattrat`），因此"保留编号但恒返 `ENOSYS`"这条备选**失效**——它会继续遮蔽 Linux 已分配的系统调用。

| 备选 | 做法 | 代价 |
|---|---|---|
| **A 一次性全部删除（采纳）** | 快 | 需同步清理用户态库、测试与文档 |
| B 分三批（身份 → 用户态；存储 → 存储层；杂项 → 既有 syscall） | 稳 | 需要批次追踪 |
| C 保留编号但恒返 `ENOSYS` | —— | **已失效**：与 Linux 撞号，且与"整体作废"语义不符 |

### OQ-7 审计出口的形态与"特权主体"的界定 ［用户裁定 · 选 A］

**裁定。** 采用 A：`/proc` 只读节点，复用既有 POSIX 面。接受"procfs 可见即部分暴露"这一代价；读权限的粗分方式与"只暴露结论、不暴露策略表"的约束仍按本章口径执行。

**备选与代价。**

| 备选 | 形态 | 代价 |
|---|---|---|
| A `/proc` 只读节点（AI 倾向） | 复用既有 POSIX 面 | procfs 可见即部分暴露，读权限只能靠 uid 粗分 |
| B 特权域专用的内核环形缓冲 + 一次性拷出 | 不暴露结构 | 需要新的读取路径，验证成本中等 |
| C 独立审计设备节点 | 类似 `/dev/kmsg` | 可见性最高，与"隐身"冲突最大 |

### OQ-8 失效纪元的粒度与在途凭据清扫 ［用户裁定 · 选 D］

**裁定。** 采用 D：主体侧每域一个纪元，降权即递增；客体侧不引入 per-inode 纪元，改用挂载点的标签版本号（与 OQ-13 路径派生同构；M1 不实例化该字段，因为尚无运行期重挂载，见"落地约束"章）。

三条落地口径：

- **纪元挂在域对象上，不挂在进程上。** `fork` 出的子进程指向同一域对象，天然共享纪元；`exec` 时按转移规则决定是否换域——换域即独立纪元，留在原域则继续共享。这样"降级连带"不是一条规则，而是共享对象的自然结果，不需要遍历进程树通知。
- **每次使用都校验（A2）。** fd 与 VMA 各自携带签发时的 `issued_epoch`，`read` / `write` 与缺页时比较一次整数，不查表、不加锁。
- **`fork` 不继承纪元过期的 VMA。** 每个 VMA 一次整数比较，堵住"降级后 `fork` 子进程以已驻留页延长窗口"这条传播路径。

主动 unmap（降级时遍历 VMA + TLB shootdown）不在 M1 实现：策略固定于启动期且不做检测，降级缺少运行期触发源；若将来允许运行期策略更新或引入可信的降级触发源，此项必须重新评估。高敏标签禁止 `mmap` 同属可选收敛手段，不进第一阶段，也不在策略格式里预留字段。已驻留页的残余窗口写入"边界"章。

**备选与代价。**

| 备选 | 粒度 | 代价 |
|---|---|---|
| A 全局纪元 | 全系统 | 一次降权误伤全部域 |
| B 每主体纪元 | 每个域 | 凭据结构变大，需定义降级传播与继承 |
| C 每凭据过期时间 | 每条授权 | 依赖时钟可信度，无法表达"立即全部作废" |
| **D 主体纪元 + 挂载代次（采纳）** | 主体按域、客体按挂载点 | 需要给挂载点维护版本号；不覆盖 per-file 重标 |

### OQ-9 "关键域"清单与维护归属 ［用户裁定 · 选 C］

**裁定。** 采用 C：内核不内置任何"关键域"概念（这与"内核不认识域名"一致），只提供机制；仓库内附一份示例策略，覆盖身份认证、网络入口、存储格式化三域，随代码维护。这样既不侵入原则，也保证默认交付有可跑的策略。

**备选与代价。**

| 备选 | 范围 | 代价 |
|---|---|---|
| A 最小集：身份/认证、网络入口、存储格式化（AI 倾向） | 3 类左右 | 覆盖窄，守护进程类提权入口可能漏在外 |
| B 中集：A + 设备管理、模块加载、时间 | 6 类左右 | 维护成本明显上升 |
| C 内核不内置清单，由策略发行方决定 | 外部定义 | 默认交付没有可用策略 |

### OQ-10 socket 客体标签的粒度与网络栈改造范围 ［用户裁定 · 选 B］

**裁定。** 采用 B：按对端地址段映射标签，策略表里是"地址段 → 标签"的前缀规则，内核只做前缀匹配，仍是无状态判定。C（连接级）排除，它需要连接跟踪状态，与"判定是无状态纯函数"直接冲突。

对"下载过程中切换文件服务器导致对端地址跳变"的处置：**每次 `connect` 都是独立的一次建引用判定，地址变化本身不触发任何异常判断**——SGEG 没有"连续性检测"，也不做"上一次可信所以这一次继承"的推断。只要新地址与旧地址落在同一策略类（例如同属"公网 HTTPS 段"），行为与不切换完全一致；若策略按精确 IP 编写，切换就会被误拒，这是**策略编写粒度问题**，不是机制问题。另需明确边界：地址段允许不等于服务器可信，服务方身份由用户态 TLS 证书校验承担，SGEG 不做中间人检测。

实施前仍需核实：socket 对象模型与生命周期、fd 身份是否可用 `Handle + gen`、网络子系统是否允许"网络问策略"而不反向依赖。

| 备选 | 做法 | 代价 |
|---|---|---|
| A 创建时打"外部 / 内部"单一标签 | 最简 | 无法区分回环、局域网、互联网 |
| B 按对端地址段细分 | 地址段 → 标签映射 | 需要地址空间映射，IPv6/NAT 处理复杂 |
| C 引入连接级标签 | 每连接一个标签 | 需要连接跟踪状态，与"判定是无状态纯函数"冲突 |

### OQ-11 L3 有状态判据的启用粒度 ［用户裁定 · 选 D］

**裁定。** 采用 D：只标注客体，主体侧直接用既有域标签，不再引入第二套主体标注。信息流的本质是污点跟着数据走，客体标注是必需的；"主体能读什么密级"由域标签承担已经足够。

| 备选 | 标注对象 | 代价 |
|---|---|---|
| A 按主体标注 | 域 | 客体未标注时信息流判据退化 |
| B 按客体标注 | 文件 / socket | 源侧未标注时无法判断污点来源 |
| C 主体 + 客体双向标注 | 两侧 | 判据完整，策略编写与维护成本最高 |
| **D 客体标注 + 主体用域标签（采纳）** | 客体 | 不新增第二套主体标注，成本接近 B |

### OQ-12 客体抽象薄还是厚 ［用户裁定 · 选 A］

**裁定。** 采用 A：两个 trait 的薄抽象——"主体标签解析"（执行域 → 标签）与"客体标签查询"（对象 → 标签），不做 LSM 式注册表。**trait 只回答标签，不承载 `epoch` / `gen`**：纪元归主体域对象、世代号归进程对象。判据是"删掉文件系统后 SGEG 仍然成立"；代价是一次性的间接层。

### OQ-13 文件标签走 per-inode 还是路径派生 ［用户裁定 · 选 B］

**裁定。** 采用 B：路径派生，不持久化。第一阶段因此不被 EGFS 的 xattr 缺陷与崩溃一致性阻塞；语义弱化（hardlink / rename / bind mount 下标签随路径变、无 per-file 例外）被明确接受。per-inode 保留为后续可选的显式覆盖，不是第一阶段的依赖。

### OQ-14 进程客体是否进入第一阶段 ［用户裁定 · 选 A］

**裁定。** 采用 A：进入第一阶段，顺序为进程 → 文件 → socket。理由是它不需要文件系统配合、判定点现成（`process_vm` 的 `check_access`、`kill`），且能以最小改动跑通完整闭环。

### OQ-15 委托深度的档位定义 ［用户裁定 · 选 B］

**裁定。** 采用 B：四级档位（0 未知 / 1 未验证 / 2 已验证 / 3 引导链背书）。内核只做档位比较，档位与具体策略谓词的映射由策略作者决定，不进内核语义。

### OQ-16 `pwm` 是否等价于安全域 ［用户裁定 · 选 B］

**裁定。** 采用 B：在 `pwm` 之外另加独立的 `label` 字段，不复用 `pwm`。`pwm` 的语义（会话标识？账户标识？安全域？）仍未核实，直接复用会把账户语义带回判定输入，与"判定输入不含 uid"冲突。

## 已识别缺口

这一章收集设计评审中识别出、但未进入 OQ 编号的缺口。每条给出候选处置、理由与裁定。G1–G4 若不定，第一阶段会带着直接绕过面；G5–G9 需在第一阶段动工前定义；G10–G12 可延后。

### G1 路径派生的链接类绕过 ［用户裁定 · 选 B］

**场景。** 路径派生只定义了"标签来自路径"，没有定义规范化规则。四条可用手法：`link` 把敏感文件硬链到宽松目录；符号链接指向敏感目标；`rename` 把文件移进宽松目录；bind mount 让同一目录有两个挂载点。若标签按字面路径派生，这四条都是提权路径。

**选项。**

- A 只做规范化：按 `resolve` 后的最终路径派生、符号链接递归解析、跨挂载取最终挂载点的标签；`link` / `rename` / `mount` 本身不单独判定。代价最小，但搬运行为不受控。
- B A + 把 `link` / `rename` / `mount` 列为判定点（与"建引用时刻判定"同构）。搬运需要授权，搬完后标签随新路径走。
- C B + 标签回到按 inode 派生（即 OQ-13 的 A），彻底消除路径歧义。代价是被 EGFS 的 xattr 缺陷阻塞，第一阶段无法开工。

**理由。** A 只做规范化，拦不住 `link` / `rename` / `mount` 的搬运——把敏感文件搬进宽松目录不是读取，规范化对它无效；C 回到 inode 标签会被 EGFS 的 xattr 缺陷阻塞，第一阶段无法开工。B 是唯一既不依赖 inode 标签、又能把搬运纳入判定的选项，且不改变这些操作的既有语义。

### G2 `ioctl` 与设备文件 ［用户裁定 · 选 B］

**场景。** 判定挂在 `open`，但设备文件的价值全在 `open` 之后：`ioctl` 可以重配网卡、擦除块设备、切换 TUN 模式。一个"只读打开"的块设备仍然能被 `ioctl` 打穿。

**选项。**

- A 不处理，只在 `open` 判定，列为已知缺口。
- B 设备类客体（块 / 字符设备）上，非特权域的 `ioctl` 一律拒绝，除非策略显式允许。
- C 引入 per-`ioctl` 权限类（SELinux 式），策略表增加 `ioctl` 维度。

**理由。** 对设备文件而言，"只在 `open` 判定"近似等于没判定——打开之后能做什么全由 `ioctl` 决定。per-`ioctl` 权限类会给策略表增加一个维度，破坏"判定可穷举"。B 用一条粗规则换取覆盖，误拒由策略白名单收敛。

### G3 接收路径的主体归属 ［用户裁定 · 选 A］

**场景。** 设计说"被动、跑在调用者上下文"，但网络**接收**路径不在任何进程上下文：包到达时由谁判定？不定这一条，OQ-10 的 socket 标签在接收方向是空的。

**选项。**

- A 归属 socket 创建者的域，在 `bind` / `connect` 时绑定，接收判定用该域。
- B 把内核网络处理当作独立域，接收方向只做客体侧判定。
- C 接收方向不判定，只判 `accept` / `connect`。

**理由。** 四家的主体标签都由上一环注入（登录、login、launchd），接收路径同样需要一个可追责的主体，socket 创建者是最自然的锚点。B 造出一个无主的内核域，出事无法归因；C 让接收方向留空，与 OQ-10 的 socket 标签矛盾。

### G4 第一阶段 IPC 绕过面 ［用户裁定 · 选 A］

**场景。** 第一阶段不做 pipe / 共享内存 / `SCM_RIGHTS` 客体，两个进程可以通过这些通道完全绕过 SGEG 交换数据。这是范围选择，不是 bug，但文档现在没有声明。

**选项。**

- A 边界章明写"第一阶段存在 IPC 绕过面"，不实现。
- B 第一阶段加 pipe 客体（内存侧标签）。
- C 第一阶段加共享内存客体。

**理由。** 缺口的可见性与 fail-open 的前提同源——机制能接受放行，是因为留下了证据；范围缺口同样应被明写。B / C 会把第一阶段撑成半个 IPC 子系统，扩大强制面。

### G5 `execveat` / `fexecve` 的标签来源 ［用户裁定 · 选 A］

**场景。** 用 fd 执行时拿不到路径，而转移规则的输入是"可执行文件标签"。

**选项。**

- A 转移规则接受 `fd → inode → 标签`，与路径来源同构。
- B 只支持路径 `exec`，对 `execveat` 返回 `ENOSYS`。

**理由。** 判定输入本就是对象而不是路径，接受 `fd → inode → 标签` 是零成本；只支持路径 `exec` 会让 `execveat` 变成逃避转移规则的绕过面，属于制造缺口而不是减少工作。

### G6 `setuid` / `capset` 与纪元的关系 ［用户裁定 · 选 A］

**场景。** 兼容红线写了"`setuid` 优先于标签转移"，但没有定义能力变化是否触发纪元递增。

**选项。**

- A 纪元只由**标签变更**递增，能力变化不递增。
- B 任何凭据变化都递增。
- C 引入独立的凭据纪元，与标签纪元分开。

**理由。** 纪元表达的是"授权签发后被撤销"，不是"凭据发生变化"。任何凭据变化都递增，会让降权守护进程在丢能力的瞬间作废全部 fd，直接踩中兼容红线；独立的凭据纪元则会引入第二套需要论证的状态。

### G7 策略部分加载 ［用户裁定 · 选 A］

**场景。** fail-open 只定义了"加载失败"，没定义"加载了一半"。

**选项。**

- A 原子加载：整表成功才生效，否则视同失败并留证据。
- B 逐条生效，部分可用。
- C 失败回滚到上一版策略（需要持久化上一版）。

**理由。** fail-open 隐含"系统仍自洽"这一前提；半张策略表既不能推理也不能审计，比完全不加载更危险。回滚方案需要持久化上一版策略，与"策略放只读镜像"的既定做法冲突。

### G8 未标注客体的默认标签 ［用户裁定 · 选 A］

**场景。** "启用即默认拒绝"没有说明未标注客体归哪个标签。

**选项。**

- A 显式 `unlabeled` 标签，只对 unconfined 域放行。
- B 继承父目录标签。
- C 一切未标注对象默认拒绝。

**理由。** 只有存在显式的 `unlabeled` 档，"默认拒绝"与"系统可用"才能并存。路径派生下父目录总有标签，继承规则会掩盖"挂载点未配置"这一真实缺失；全拒则让策略不完整直接等于系统不可用。

### G9 纪元回绕与域对象生命周期 ［用户裁定 · 选 A］

**场景。** 纪元递增会回绕；域对象何时释放、由谁释放未定义；与 mm 锁、fd 表锁的先后未定义。

**选项。**

- A `u64` 纪元 + 域对象引用计数（最后一个进程离开即销毁）+ 锁序写入锁序文档。
- B `u32` 纪元 + 回绕时强制换代。

**理由。** `u64` 消除的是低频但不可恢复的一类故障；引用计数不是优化，而是域对象被 `fork` 共享之后的必然要求；锁序入档是 `audit_deadlock_matrix` 的既有要求。

### G10 命名空间下的进程身份 ［用户裁定 · 选 A］

**场景。** `(pid, gen)` 只在单个 pid namespace 内唯一，跨 namespace 判 `kill` 会冲突。

**选项。**

- A 身份扩为 `(namespace_id, pid, gen)`。
- B 只支持单一 pid namespace。
- C 使用全局唯一 tid。

**理由。** 判定不能张冠李戴，身份必须全域唯一。单一 namespace 的限制一旦引入命名空间即失效；全局 tid 的语义尚未核实。本项以"Edgine 已实现 pid namespace"为前提，未实现则可整体推迟，不影响第一阶段。

### G11 策略与编译器自身的完整性 ［用户裁定 · 选 A + C］

**场景。** 第一阶段无签名，谁改策略文件谁就改防护。

**选项。**

- A 接受该风险并写入边界章。
- B 策略签名，验证密钥来自引导链。
- C 策略文件放只读镜像（ramfs / initramfs）。

**理由。** 策略签名依赖引导链提供密钥，而引导链目前是空壳——把完整性建立在尚不存在的机制上属于依赖倒置。只读镜像把攻击面从"运行期改文件"降为"改镜像"，剩余风险在此显式承认。

### G12 判定函数自身失败 ［用户裁定 · 选 A］

**场景。** `fail-open` 是给"加载失败"的，不一定要延伸到"判定中途表缺失 / 索引越界"。

**选项。**

- A 视为加载失败，整模块转 permissive 并留证据。
- B 每次判定失败即拒绝（局部 fail-closed）。
- C 跳过该判据继续。

**理由。** 这是故障域问题：单点数据损坏不应变成行为差异。转 permissive 保住可用性与证据，与 fail-open 同源；局部 fail-closed 会让一个坏表项变成无法诊断的随机拒绝，跳过判据则会静默放行。

## 已定决策汇总

- **［用户裁定］定位**：内核安全模块 / 机制，不是安全服务；类比 SELinux；控制面走文件而不是 syscall。
- **［用户裁定］隐身三层**：不被调用（必须）、不改变既有语义（必须）、完全不可观测（不做且有害）；保留只读内省面。
- **［用户裁定］零新增 syscall**；现有 `SYS_SGEG_*` 整体作废，不改造。
- **［用户裁定］文件名**：`docs/design/sgeg-design.md` 不带版本后缀。
- **［用户裁定］跳数定位**：不具主判据地位，降为证据项之一；只在审计字段与上限参数两个位置存在。
- **［用户裁定］多判据组合**：单调收窄——全部通过才允许，任何判据只能把结果推向更严，不得加权打分，不得由拒改允。
- **［讨论共识］四原语**：主体标签、客体标签、转移规则、判定；内核不认识标签名与权限名。
- **［讨论共识］三条减法**：策略语言、身份、可信启动都不进内核；可信启动是前提而非并列组件。
- **［讨论共识］身份路线 A**：判定输入不含 uid；SGEG 只使用身份，不拥有身份；账户与登录移用户态。
- **［讨论共识］主体标签注入点**：`exec`，由父进程或启动器决定；`fork` 继承，不做递增。
- **［讨论共识］兼容红线**：`setuid` 优先、`/proc` 读法不变、`ptrace` 可用、`ld.so` 不被挡、必须有 unconfined 默认域。
- **［讨论共识］强制模型**：标签 + 表；保留 `CAP_*` 并叠加；默认关闭、启用即默认拒绝；加载失败 fail-open + 响亮证据。
- **［讨论共识］三值结果**：允许 / 允许但受限 / 拒绝；"最低档"不等于拒绝，只等于能力上限降低；检测到篡改是硬拒绝。M1 退化为二值 + 域级 permissive。
- **［讨论共识］判定点形状**：入口唯一（`resolve → authorize → publish`），标签存储按对象类型分散；文件系统的 `open_by_handle_at` 必须收敛进同一出口。
- **［讨论共识］类型防线射程**：`Witness` 只覆盖 crate 内部纯 Rust 链路；`extern "C"` 主路径靠结构唯一出口 + 审计数出口数量。M1 不实现 `Witness`。
- **［用户裁定］客体模型**：统一的标签查询接口 + 按对象类型的实现（`epoch` 归主体域对象、`gen` 归进程对象）；采用两个 trait 的薄抽象（OQ-12 选 A），不做 LSM 式注册表。
- **［讨论共识］进程作为一等客体**：主体/客体双角色、判定不对称；线程只做归因粒度，不做隔离粒度。
- **［讨论共识］客体顺序**：进程 → 文件 → socket；socket 最后是因为它需要先做客体抽象改造。
- **［讨论共识］传播链形态**：用格（逐跳取 min）替代链长累加；每跳只能收窄；缺链按最低档处理；跳数只进审计与上限参数。M1 无 provenance，`tier` 字段不实例化。
- **［讨论共识］`fork` 不是委托**：分叉加性、委托乘性；fork 不计深度；fork 炸弹归资源层。
- **［讨论共识］多判据分层**：L1 静态表 → L2 动态证据 → L3 有状态判据；L3 只对被标注对象启用。
- **［用户裁定］第一阶段范围**：静态表 + 纪元 + 进程客体判定 + 文件客体判定（路径派生）；档位恒为域档位，配额待 cgroup 接线。
- **［讨论共识］误拒控制五层**：不判定（unconfined）、只记不拒（逐域 permissive）、未知降级、可读反馈、粗粒度起步。
- **［讨论共识］豁免形态**：只允许 permissive 域与策略规则本身；`dontaudit` 与运行时布尔开关不采用。
- **［讨论共识］失败处置**：fail-open 必须留证据；enforcing 上线前必须先跑 permissive 收集"本会被拒"清单。
- **［讨论共识］边界**：恶意用户态程序靠域分离；供应链植入归完整性度量；内核后门归架构隔离；被劫持进程分代理层（第二阶段）与直接层（第一阶段）；总体定位为损害面收敛而非检测。
- **［讨论共识］审计出口**：收在内核侧、单向、只暴露结论。
- **［讨论共识］失效纪元**：档位管"传递是否合理"，纪元管"现在是否有效"；使用端比较 `(域标识, 纪元)` 一对值。
- **［讨论共识］Rust 设计规则**：返回凭据而非布尔；操作接受对象而非路径；标签类型分离且构造器在 TCB 侧；策略为不可表达非法状态的枚举；跨边界对象统一 `Handle + gen`。
- **［讨论共识］网络边界不做防火墙**：频次、状态、信任边界三条硬性不匹配；只保留稀疏的 `connect` / `bind` / `accept` 判定、socket 客体标签、`SCM_RIGHTS` 传递判定与网络栈域隔离。
- **［讨论共识］SGEG 判额度、策略表判权限**：策略表不判"允不允许 fork"，配额判据只回答"已用掉多少"。
- **［用户裁定］客体抽象**：A 薄抽象（主体标签解析 + 客体标签查询两个 trait，只回答标签，不承载 `epoch` / `gen`）。
- **［用户裁定］文件标签路线**：B 路径派生，不持久化；per-inode 留作后续可选覆盖。
- **［用户裁定］进程客体**：进入第一阶段，顺序为进程 → 文件 → socket。
- **［用户裁定］拒绝行为**：D `EACCES` + 审计 + 速率限制；限流依赖资源记账接线，之前只生效前两项。
- **［用户裁定］策略所有权**：C 启动期固定，改策略需重启。
- **［用户裁定］存量 syscall 处置**：A 一次性全删，同步清理用户态库、测试与文档。
- **［用户裁定］provenance 时机**：B 第一阶段稳定后做。
- **［用户裁定］审计出口**：A `/proc` 只读节点。
- **［用户裁定］档位级数**：B 四级（0 未知 / 1 未验证 / 2 已验证 / 3 引导链背书）。
- **［用户裁定］主体标签挂点**：B 在 `pwm` 之外另加独立 `label` 字段，不复用 `pwm`。
- **［用户裁定］客体粒度**：A 第一阶段只覆盖文件与进程；pipe / socket 留到 M2。
- **［用户裁定］失效纪元**：D 主体每域纪元 + 客体按挂载点代次；纪元挂域对象（`fork` 共享、`exec` 按转移规则换域）；fd 与 VMA 携带签发纪元，使用时比较一次整数；`fork` 不继承过期 VMA；主动 unmap 不实现，列为依赖 OQ-3 的延后项。
- **［用户裁定］"关键域"清单**：C 内核不内置，仓库附三域示例策略。
- **［用户裁定］socket 标签**：B 按对端地址段映射；地址跳变不构成异常，每次 `connect` 独立判定。
- **［用户裁定］L3 标注对象**：D 只标注客体，主体用既有域标签。
- **［用户裁定］降级连带范围**：纪元挂在域对象上，`fork` 出的进程共享同一纪元（连带）；`exec` 进入新域则独立（不连带）。
- **［用户裁定］M1 简化口径**：不做 `Witness`、委派深度与跳数记录、L2/L3 代码结构、`tier` 字段、三值与 `evidence` 容器、通用 `SecurityBlob`、转移规则双输入、挂载代次、高敏标签禁 `mmap`；进程侧只接 `process_vm` 与 `kill`。详见"落地约束"章的"M1 明确不做的事"。
- **［用户裁定］已识别缺口**：G1–G12 全数闭合——G1 B、G2 B、G3 A、G4 A、G5 A、G6 A、G7 A、G8 A、G9 A、G10 A、G11 A + C、G12 A；理由见"已识别缺口"章。
