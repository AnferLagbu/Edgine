# docs/ 写作规范

> 本目录的结构：`plan/`（计划/历史）+ `design/`（目标架构设计）+ `explain/`（现状/解释）+ `report/`（结果报告）。
> 本文件告诉开发者**往这四处写入/修改时的格式与组织要求**。

> **适用范围：** 本文件定义的所有格式规则**仅适用于** **`docs/`** **下文档**（`plan/*`, `design/*`, `explain/*`, `report/*`）。
>
> **AGENTS.md 是规则/指导文档，不受本规范约束，保持自然描述风格**（用 H1/H2/H3 + 表格 + 代码块 + 列表自由组织，不强制"每条带状态 \[X]/\[]"）。详见 `AGENTS.md` §7。

***

## 0. 核心原则（最重要，先看）

| 原则        | 含义                                                                 |
| --------- | ------------------------------------------------------------------ |
| **格式极简**  | 纯 Markdown，无模板，无前置 front-matter，无目录页。标题用 `#` 一级起，章节用 `##` 即可。 |
| **信息密度高** | 该写的一句不少，不该写的一句不留。没有占位符，没有"TODO: 补充"。不确定的就写"未知"。                |
| **结构自洽**  | 每个文件完整讲清楚一件事。不依赖其它未链接文件即可读。跨文件引用用相对路径。                           |
| **中文优先**  | 文档用中文写。专有名词（API/术语）保留英文。代码示例保留英文。                              |
| **可搜索**   | 关键词首次出现时加粗一次，之后不重复加粗。                                             |

不要做的事：

- 不写"前言 / 摘要 / 致谢"等空话。
- 不在文档中嵌入大段完整代码（代码应指向源文件，引用行号）。
- 不创建无人维护的索引页。
- 不为"将来可能用到"预留章节。

## 1. 文件归属规则（写之前先看）

| 写什么                   | 放哪里                                        | 文件名                                                        |
| --------------------- | ------------------------------------------ | ---------------------------------------------------------- |
| 一次提交的变更说明             | 无需独立文档                                    | -                                                       |
| 路线图 / 未来计划            | `docs/plan/`                               | `*.md`                                                     |
| 设计计划 / 迁移方案           | `docs/plan/`                               | `*.md`                                                     |
| 审计报告 / 修复报告 / 交付总结    | `docs/report/`                     | `audit-*.md` / `fix-report-*.md` / `delivery-summary-*.md` |
| 诊断 / 评估 / 测试 / 性能等结果报告 | `docs/report/`                    | `*.md`（kebab-case，见 §2） |
| 待办（跨多 commit）/ 已知问题 | `docs/plan/`                               | `fix-tasks.md` / `known-issues.md`                         |
| 架构说明 / 子系统文档          | `docs/explain/`                            | `*.md`                                                     |
| API 参考 / 教程           | `docs/explain/`                            | `*.md`                                                     |
| 论文 / 设计文档 / 参考材料      | `docs/explain/`                            | `*.md`                                                     |
| 目标架构设计 / 设计立场文档（子系统"要演化成什么样"） | `docs/design/`              | `*-design.md`                                              |

判断口诀：

- 这东西**指向未来**且**可直接执行为任务条目**（路线图 / 迁移步骤 / 待办）？→ `plan/`
- 这东西**指向未来**但讲的是**目标形态、设计立场与开放议题**（不含可执行状态追踪）？→ `design/`
- 这东西**解释现在**或**教人使用**？→ `explain/`
- 这东西是**某次执行/审计/评估/测试的结果陈述**（一次性快照，不持续维护）？→ `report/`
- 这东西是**当前这次提交**的变更？→ commit message 里说明即可，无需独立文档。

> `docs/plan/` 下既有 `audit-*` / `fix-report-*` / `delivery-summary-*` 为历史产物，原位保留不迁移；新报告一律写入 `docs/report/`。

***

## 2. 文件命名规则

- 全小写 + 连字符（`kebab-case`）。
- 单词之间用 `-`，不用 `_` 或空格。
- **文件名不带日期前缀**（日期也不写在文件内部，见 §3）。
- 同一主题多个文件用统一前缀（例：`audit-*`, `fix-report-*`）。
- 例：`framekernel.md` ✓, `FRAME_KERNEL.MD` ✗, `FrameKernel-roadmap.md` ✗。

***

## 3. 文档内部格式

> 本节结构化字段（描述/方案/状态/详情）适用于 plan/ 与 archive/ 类历史文档；design/、explain/ 与 report/ 采用自由描述风格（分别见 §5.1、§6 与 §6.1）。

### 3.1 通用结构

> 文档 = 标题 + 若干章节，每章节 = 条目列表，每条目 = 描述 + 方案 + 状态。
> 状态：`[]` = 未实施，`[X]` = 已实施。
> 详情：可选，必要时补充深入内容（代码片段/数据/参考链接）。

```
# <文档标题>

> 0-1 行核心结论。没想清楚就空着。

## <章节 1>
- **<条目名>**
  - 描述：<描述>
  - 方案：<如何做>
  - 状态：[]
  - 详情：<可选，深入内容>

- **<条目名>**
  - 描述：<描述>
  - 方案：<如何做>
  - 状态：[X]

## <章节 2>
- **<条目名>**
  - 描述：<描述>
  - 方案：<如何做>
  - 状态：[]
  - 详情：<可选，深入内容>
```

### 3.2 格式细则

| 元素 | 规则                                              |
| -- | ----------------------------------------------- |
| 标题 | H1 用一次，H2 章节，H3 子章节。不用 H4 及更深。               |
| 列表 | 用 `-` 无序列表。不用 `*` 或 `+`。嵌套缩进 2 空格。            |
| 代码 | 用围栏 \`\`\` + 语言标识。行内用 \` 单引号。                  |
| 表格 | 用 GFM 表格。列对齐只在数字列用 `---:`。                     |
| 引用 | 用 `>`。跨文件引用用相对路径：`[标题](./other.md)`。          |
| 强调 | 关键词首次出现 `**加粗**`。不用斜体。                         |
| 链接 | 优先用相对路径。外部 URL 完整给出。                           |
| 图片 | 不建议用。必要时 `![alt](./img/x.png)`，图片放同目录 `img/`。 |
| 日期 | **不使用**日期信息（不写 YYYY-MM-DD / 不写"昨天/最近/即将"）。文档状态由 git 提交历史维护。 |
| 数字 | 大于 1000 加千分位。代码中的数不加。                          |
| 缩写 | 首次出现展开："宏内核（Monolithic Kernel, MK）"。          |

### 3.3 代码引用

不复制大段代码。用以下形式指向源：

```
详见 [src/kernel/privileged/proc/user_proc.rs:810-858](src/kernel/privileged/proc/user_proc.rs) 的 `create()` 函数.
```

或在行内：

```rust
// user_proc.rs:820
let cr3_val = setup_pagetable(kproc);
```

引用代码**必须真实存在**，引用前请先 `grep` 确认行号。

**适用边界（路径新鲜度只约束“必须与代码同步”的文档）**：上述强制适用于 `docs/explain/`、`docs/design/` 与根文档（`AGENTS.md` / `README.md` / `docs/README.md`）——它们描述当前形态，路径失效即文档失真。`docs/plan/`（含 `archive/`）条目记录的是**执行当时**的代码形态（批次目标文件 / 实测行数 / 已下沉或已删除的模块），`docs/report/` 发布即冻结；这些历史路径会随后续工程失效，属正常现象，**不得为了“路径存在”而改写历史记录**（§9.2 要求 plan 同步的是状态标记 `[]/[X]`）。`tools/check_doc_paths.py` 按此边界取校验集合（按需运行，未接入 CI）。

## 5. plan/ 文档格式

主题：计划/未来/历史决策。重点是**意图、约束、状态**。

> 一个文档允许包含多个工程计划。每个工程计划 = 独立 H2 章节，章节标题 = 计划名。
> 状态：`[]` = 未实施，`[X]` = 已实施。详情：可选，必要时补充深入内容。

```
# <文档标题>

> 0-1 句话说清"为什么有这个计划 / 历史上发生了什么"。

## 工程计划 A: <计划名>
### 背景
- **<背景条目>**
  - 描述：<为何要做 / 触发了什么>
  - 方案：<应对思路>
  - 状态：[]

### 目标
- **<目标条目>**
  - 描述：<具体要达到什么>
  - 方案：<如何达成>
  - 状态：[]

### 现状
- **<现状条目>**
  - 描述：<已完成什么 / 未完成什么>
  - 方案：<下一步动作>
  - 状态：[]

### 方案
- **<方案条目>**
  - 描述：<实现思路关键决策点>
  - 方案：<具体步骤>
  - 状态：[]
  - 详情：<可选，关键设计点/参考链接>

### 待办
- **<待办条目>**
  - 描述：<具体可执行项>
  - 方案：<如何做>
  - 状态：[]

### 决策记录
- **DECISION-NNN**
  - 描述：<决策内容>
  - 方案：<原因, 替代方案及放弃原因>
  - 状态：[X]

### 变更历史
> 变更历史由 git 提交记录承载，本文档不写日期段。如需追溯，使用 `git log -- <path>` 或 `git blame`。

## 工程计划 B: <计划名>
### 背景
- **<背景条目>**
  - 描述：...
  - 方案：...
  - 状态：[]
```

要点：

- 一个文档允许包含多个工程计划。每个工程计划用 H2 章节独立，章节标题 = `工程计划 <ID>: <名称>`。
- H2 章节下用 H3 子章节（背景/目标/现状/方案/待办/决策记录/变更历史）组织条目。
- 同一文档内多个工程计划应：(1) 主题相关，(2) 互不冲突，(3) DECISION-NNN 全文档编号唯一。
- 计划随时间变化，改文档本身。**不创建** **`*-v1.md`** **`*-v2.md`**。
- 已完成 / 已废弃的计划**保留**，在状态字段标记，不删除。
- 决策记录（DECISION-NNN）一旦写入，编号永久保留，不重用（全文档唯一）。

## 5.1 design/ 文档格式

主题：目标架构设计。重点是**要演化成什么样、为什么这么选、理论根基与开放议题**。design/ 存放子系统的**设计立场文档**——它不是现状说明（那是 explain/），也不是可执行任务清单（那是 plan/），而是介于两者之间的长期设计主张：诊断结论如何推导出目标架构、架构形态的理论基础、与业界方案（MINIX / RedLeaf / Theseus 等）的取舍对比、尚未闭合的开放议题。

内容描述规则与 §6 explain 一致：纯自由描述风格（H1 标题 + H2 章节 + 自然段落 + 表格 + 代码片段 + 列表），**不使用**结构化字段（`描述：` / `方案：` / `状态：` / `详情：` 四件套禁用），**不使用**状态标记（`[]` / `[X]`），**不写末尾"变更历史"段**。

与 explain 的差异在时态与生命周期：

- **explain 写"系统现在是什么样"**（与代码同步维护，代码变了文档跟着变）；
- **design 写"子系统要演化成什么样"**（指向目标的活文档：设计推进时直接改正文本体，不建 `*-v2.md`；落地完成后按 §7 处理——稳定部分迁入 explain/，剩余工作转入 plan/ 条目，设计文档保留不删）。

要点：

- 允许写"未来形态"，但必须锚定在**设计立场**上（为什么这么设计、何时需要扩展），不写无立场的空想；
- 可执行分解一律归 plan/：design/ 讲主张，plan/ 讲施工步骤与状态；
- 引用诊断/审计结论时指向 report/ 或 plan/ 的相对路径，不把结论细节复制进 design/。

## 6. explain/ 文档格式

主题：解释现在。重点是**是什么、为什么、怎么用**。

explain 下的文档属于**解释描述类**，是面向人类读者/AI 读者的说明性文档。**完全不采用** plan/ 文档的结构化字段（`描述：` / `方案：` / `状态：` / `详情：` 四件套全部禁用），因为它们不是任务规划，而是描述性内容。采用**纯自由描述风格**：H1 标题 + H2 章节 + 自然段落 + 表格 + 代码片段 + 列表，按内容需要自由组织。适合表达设计哲学、立场说明、期望愿景、长期主义描述等内容。

要点：

- **不使用任何结构化字段**：`描述：` / `方案：` / `状态：` / `详情：` 等 plan/ 文档专属字段在 explain 中全部禁用。文档描述的是"现状"或"立场"，不是任务规划。
- **不使用状态标记**：`[]` / `[X]` 标记在 explain 中禁用（任务状态追踪不属于描述性文档）。
- **不写末尾"变更历史"段**（变更历史属于 plan/ 文档的范畴，由 git 提交历史承载）。
- 写"现在是这样"，不用"将来会改成那样"。
- 删了/改了代码，文档同步改。文档失实比缺文档更糟。
- 多文件存在时，拆成多个独立 `*.md`，用相对链接互引，**不做总目录页**。
- 例外：explain 中引用 plan 文档时，可在正文写"对应 plan/X.md §N"，但不引入 plan 的状态字段或四件套结构。

***

## 6.1 report/ 文档格式

主题：报告某次执行/诊断/审计/评估/测试的**结果**。重点是**发现了什么、结论是什么、证据在哪里**。report 存放项目**生命周期内的报告**，其用途是作为**制定计划（plan/）与启动修复工程的输入依据**——先有 report 的事实结论，再据此立 plan 条目或开修复 PR。

report 与 explain 同属描述性文档，**内容描述规则与 §6 explain 完全一致**：纯自由描述风格（H1 标题 + H2 章节 + 自然段落 + 表格 + 代码片段 + 列表），**不使用**结构化字段（`描述：` / `方案：` / `状态：` / `详情：` 四件套禁用），**不使用**状态标记（`[]` / `[X]`），**不写末尾"变更历史"段**。

与 explain 的差异仅在定位与生命周期：

- **explain 写"系统现在是什么样"**（持续维护的活文档，代码变了文档跟着变，见 §6）；
- **report 写"某次检查/执行的结果快照"**（发布即冻结：后续发现新结论应另开新报告或文内追加"补充结论"节，不因代码演进而回头修改正文事实陈述）。冻结的是"当时观测到的事实"，不冻结其指导价值——它仍作为后续 plan/修复的溯源依据被引用。

内容要求：

- 标题下用 `>` 0-1 行给出**核心结论**（通过/失败/风险项数等），读者不必读完全文才知道结果。
- 结论必须有**可验证证据**：文件路径 + 行号（先 grep 确认，见 §3.3）、测试命令与输出、数据表格。
- 引用历史 plan/ 文档时用相对路径，不引入其状态字段。

***

## 7. 修改现有文档

- 小修：直接改，**不写文档内"变更历史"**；plan/ 与 explain/ 文档均不强制文档内变更历史段。
- 大改（结构调整 / 重写）：在文档顶部 `<>` 标记后，写一行 `> **重写**：简述改动原因`。
- 推翻：在文档顶部加 `> **DEPRECATED**：废弃原因。见 [新文档](./new.md)`。不删除。
- 文档状态由 git 提交历史维护（`git log -- <path>` / `git blame`），文档内不再写日期。

## 8. 自检清单（提交前过一遍）

- [ ] 文档归属正确（plan / design / explain / report）？
- [ ] 文件名 `kebab-case`，无日期前缀？
- [ ] 文档内无任何日期信息（YYYY-MM-DD / 时间戳 / "昨天/最近/即将"）？
- [ ] H1 仅一个，H2 起章节，无 H4+？
- [ ] 代码引用行号已用 `grep` 验证？
- [ ] 跨文件链接用相对路径且目标存在？
- [ ] plan 文档状态字段已更新？
- [ ] explain / report 文档无状态标记（[] / [X] / 状态：）？
- [ ] explain 文档与代码现状一致？（report 为冻结快照，不适用本条）

## 9. 反例（不要这样写）

不要写前言：

```
# 内核架构文档

本项目是一个创新的宏内核操作系统，由本团队自主研发，...
> 前言段不是规范要求，是冗余。
```

不要写空模板：

```
## 概述
(待补充)

## 详细设计
(待补充)
```

不要在文档里粘大段代码：

```
下面是 xxx 函数的完整实现：
\`\`\`rust
fn foo() {
    // 200 行 ...
}
\`\`\`
```

（应改为指向源文件链接 + 1-3 行关键片段）

不要写"将来"而不写日期：

```
> 未来我们将支持 ...
```

（应改为指向对应 design 文档或 plan 文档，或直接删除。"将来"的正当归属是 design/（目标形态主张）与 plan/（可执行步骤，保持状态：[] 字段）；explain 文档中不描述"将来"）
