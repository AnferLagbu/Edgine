# 简化实现与稳定性评估

> 结论：`docs/explain/linux-compat-philosophy.md` 列出的五项「不引入 Linux 复杂度」的替代实现，本身不是「偷工减料的简陋」——多数在容量耗尽时**失败闭合**（返回 `None` / 错误，而非静默出错或 panic），这是稳定性的正确方向。真正的隐患集中在两类：**容量常数过小且无淘汰策略**，以及**持锁跨层调用**。另有一项不属于「简化」而属于「省略安全前提」：无 DMA zone 且无 IOMMU 时的设备可寻址范围失配。

**快照与基线**：HEAD `a7b6d87b`（2026-11-13 20:26 +0800），取证日期 2026-11-14。全程只读：仅阅读源码与静态检索，未构建、未运行负载、未修改任何文件。

## 一、评估方法

对每一项回答三个问题：

1. **耗尽/异常时是失败闭合还是静默出错**（决定「简化」是否安全）；
2. **容量常数与真实工作负载的比值**（决定能力边界在哪）；
3. **锁的作用域是否跨越模块边界**（决定并发下是否稳定）。

三项都过关才算「简约但稳定」；第 2 项不过关属能力上限，第 3 项不过关属并发正确性。

## 二、Page Cache：固定 64 桶 × 16 条

**实现事实**

- `PCACHE_HASH_BUCKETS = 64`、`PCACHE_BUCKET_CAPACITY = 16`（`src/kernel/privileged/mm/pcache.rs:129-131`），全局静态数组 `[IrqSpinLock<PageCacheBucket>; 64]`（`:312-313`），哈希取低 6 位（`:320`）。
- 总容量 = 64 × 16 = **1,024 个 4 KiB 页 ≈ 4 MiB**。
- 桶满时 `insert` 在 `:194-195` 直接 `return None`，向上传播为分配失败；**没有淘汰路径**。

**判定**

- 失败闭合：✅。不会静默丢数据，不会 panic，调用方得到明确失败。
- 容量比值：❌。4 MiB 的全局页缓存不足以顺序读取一个百 MB 级文件；表现不是「变慢」，而是中途 `ENOMEM`。
- 锁作用域：⚠️。`insert` 在**持有 bucket 自旋锁**期间调用 `pmm::get_pmm().alloc_page()` 并执行 `zero_phys_page()`（`:198-207`）。这构成 `pcache 锁 → PMM 锁` 的嵌套，且持锁做整页清零（数百纳秒级临界区）。若存在任何 `PMM → pcache` 的反向路径即为死锁；即使不存在，长临界区在高并发下会产生延迟尖刺。

**结论**：安全性合格，能力与延迟不合格。这是五项中最可能被真实负载（编译、解压、大文件拷贝）直接撞破的一项。

## 三、Swap：固定 4096 槽 + 256 项 LRU

**实现事实**

- `SWAP_MAX_SLOTS = 4096`（`src/kernel/privileged/mm/swap.rs:115`）≈ **16 MiB**。
- `LRU_CAPACITY = 256`（`:311`），`active` / `inactive` 为定长数组（`:304-307`）。
- `alloc_slot` 遍历位图取首个空闲槽，无空闲时 `None`（`:223-232`），调用方以 `?` 传播（`:585`）。
- `write_slot` 同步拷贝整页（`:588-589`），无异步 I/O。

**判定**

- 失败闭合：✅。槽位耗尽返回失败，不越界、不覆盖在用槽。
- 容量比值：❌。16 MiB 换出空间对应 4 MiB 页缓存，二者量级都远低于任何真实内存压力场景。
- 决策质量：⚠️。LRU 只跟踪 256 项，而槽位有 4,096 个——**淘汰算法看到的视图只有全局的 1/16**。「LRU」这个名字承诺的全局近似没有兑现，实际是一个局部窗口策略。
- 锁作用域：未见跨层调用；同步整页拷贝会拉长缺页延迟，但正确性无虞。

**结论**：fail-closed 正确，但容量与淘汰视野双低。它更像是「swap 机制的语义验证器」，不是可用的换出后端。

## 四、EEVDF：BTreeSet + 双账 + 加权和

**实现事实**

- 运行队列键为 `(vruntime, pid)`（`src/kernel/privileged/proc/eevdf.rs:286-289`），**用 pid 破平局**。
- 另有 `tree_ledger` / `running_ledger`（`BTreeMap<Pid, QueuedTask>`）与 `tree_weight` / `running_weight`、`tree_sum_w_vr` / `running_sum_w_vr`（`u128`）双账（`:296-307`）。
- `min_vruntime` 为 `AtomicU64` 且字段私有，只允许经 `floor()` 读、`advance_floor()` 写（`:290-293`）。
- 模块头注释记录了历史事故：旧 `boost_all_vruntime` 「折叠相对次序且与任务自身 vruntime 分域」已被删除（`:16-18`，DECISION-099）。
- 队列由 `PerCpuSched.eevdf_rq: Mutex<EevdfRunQueue>` 保护（`src/kernel/privileged/proc/scheduler.rs:234-237`）。

**判定**

- 正确性设计：✅。键含 pid 避免了「同 vruntime 任务互相覆盖」这一类经典缺陷；双账 + 加权和使「树结构」与「记账」可交叉校验；下界字段私有化防止调用点重新引入「重设」语义。这是五项中**唯一被真实 bug 打磨过且留下了防回归结构**的一项。
- 容量：无硬上限，BTreeSet 随任务数增长，无容量悬崖。
- 并发：⚠️。粗粒度 `Mutex` 意味着入队/出队/记账全串行；跨核迁移的记账一致性（注释中的 IE5「原样携带」）是设计者自己标注的敏感面。

**结论**：不属于「简约不稳定」，反而属于「用显式记账替代 Linux 隐式复杂度」的正例。风险在锁粒度与跨核一致性，不在算法简化。

## 五、无 zone / gfp_t：省略了一个安全前提

**实现事实**

- 全仓无 `ZONE_DMA` / `zone` / `GFP_*` 的分配分支；PMM 以 `IrqSpinLock` 保护（`src/kernel/privileged/mm/pmm.rs:33`、`:2719`）。
- 检索 `bounce` 仅命中用户拷贝缓冲（`functions/fs/handle.rs`、`net/syscall.rs`），**与设备 DMA 无关**。
- IOMMU 侧 `get_dmar_drhd_list()` 在 `src/kernel` 内零消费者（既有审计结论，本快照未变）。

**判定**

- 中断上下文安全性：✅。`IrqSpinLock` 保证分配路径不睡眠，因此「没有 `GFP_ATOMIC`」在本设计中不构成死锁风险——这是简化得合理的一处。
- 设备可寻址范围：❌。没有 DMA zone、没有「按设备地址宽度分配」的接口、也没有 bounce buffer。在 IOMMU 未编程的前提下，驱动取得高于设备可寻址位宽的内存时，设备会向错误物理地址发起 DMA——这不是功能缺失，是**内存破坏风险**。

**结论**：这是五项中唯一「简化直接吞掉了安全前提」的一项。它不会在无 DMA 设备的环境里暴露，但一旦接入真实网卡/存储控制器（而非 virtio 的半虚拟化假设），风险立即实体化。

## 六、COW 计数收敛到 PMM 帧计数

**实现事实**

- 计数面下沉到 PMM：`frame_inc` / `frame_dec` / `frame_ref_count`，按 pfn 索引（`src/kernel/privileged/mm/cow.rs:22`）。
- `cow_handle_fault` 把「持有计数判定 + 映射改写 + 帧归还」放在**同一临界区**（`:486-513`），`should_reuse = frame_ref_count(...) <= 1`。
- 不引入 per-VMA `anon_vma` + rmap 反向映射。

**判定**

- 并发正确性：✅。「判定与动作同临界区」正是避免 COW 与 fork/回收竞态的关键，这个设计选择是对的。
- 可诊断性：⚠️。映射持有、页缓存持有、COW 共享三种语义压进**同一个计数器**。任何一方漏减不会立即崩溃，而是变成静默泄漏；过早减则是 use-after-free。Linux 保留 rmap 不只是为性能，也是为了让「谁还持有这一页」可枚举——省掉它，等于省掉了故障时的解释能力。
- 语义正确性：取决于三处使用是否共享同一套增减不变量，本次未做跨模块全量核对，只能确认设计意图是统一的。

**结论**：设计正确，风险在「单计数器 + 无反向映射」使错误难以定位，而非错误更易发生。

## 七、汇总

| 项 | 失败闭合 | 容量/视野 | 锁与并发 | 综合 |
|---|---|---|---|---|
| Page cache | ✅ | ❌ 4 MiB 无淘汰 | ⚠️ 锁内调 PMM + 清零 | **最可能被负载撞破** |
| Swap | ✅ | ❌ 16 MiB，LRU 视野 1/16 | ✅ | 语义验证器，非可用后端 |
| EEVDF | — | ✅ 无硬上限 | ⚠️ 粗粒度 Mutex | **正例**，非简陋 |
| 无 zone/gfp | ✅（IRQ 安全） | — | — | ❌ 省略 DMA 安全前提 |
| COW 单计数器 | — | — | ✅ 同临界区 | ⚠️ 可诊断性下降 |

三类隐患的性质不同，不能合并成「简化导致不稳定」一句话：

1. **能力上限**（page cache / swap 容量）：稳定但撑不住真实工作负载，表现为失败而非错误结果；
2. **并发正确性**（pcache 锁内跨层调用与长临界区）：需要完整锁图分析才能定性，是唯一可能产生死锁的项；
3. **安全前提缺失**（无 DMA zone + 无 IOMMU）：在真实设备上产生越界 DMA 写，是唯一可能产生内存破坏的项。

## 八、对计划的意义

- 这份简化清单的**方向是自洽的**：用显式记账与失败闭合替代 Linux 的策略层，适合「验证架构」而非「承受负载」。
- 但不能把「0.1 跑通一个静态程序」读成「负载下稳定」。0.1 的工作负载（单个静态程序、少量文件 I/O）不会触达 4 MiB 页缓存上限，也不会触发设备 DMA 越界——**这两项风险在 0.1 的验收面上不可见**。
- 若要进入「可承受负载」阶段，三项需要分别处理：容量与淘汰策略（能力面）、pcache→PMM 锁序（并发面）、DMA 可寻址范围与 IOMMU（安全面）。它们与 0.1 的接线/外部程序工程正交，不宜混入同一批次。
